# 段階 1B: カルテ・処方・マスタの土台（2026-11-09）

`replicate-plan-20261109.md` の段階 1B の実装メモ。データと API の土台だけで、画面の作り直しは段階 2B で行う（今の編集画面は最小限の手直しで動くようにしてある）。

## 1. 処方・オーダーの Rp（まとまり）とコメント行
- 処方の行・オーダーの行に任意の `rpId`。同じ `rpId` の行が 1 つの Rp。**`rpId` の無い古い行は 1 行で 1 Rp** として読む（形は変えない）。
- 保存のとき、同じ Rp の行は最初に出てきた位置にまとめる（Rp の中の順番は保つ）。
- 処方の Rp の共有項目 `RP_SHARED_FIELDS` = 院内外・用法・1 日回数・日数・眼。**Rp の先頭の薬剤行の値を、同じ Rp のほかの薬剤行にそろえる**（デジカルの「Rp の下の行に用法・日数」と同じ意味）。行ごとに値を持つので、会計 CSV・印刷・点眼本数の計算はそのまま動く。
- コメント行: `{ kind: "comment", rpId, text, scope }`。`rpId` は必須（どの Rp のコメントか分からないものは受け付けない）。`scope`: `free`（処方箋・レセプトに載せる。既定）/ `chart`（カルテだけ）。オーダーのコメント行は `orderId` も持つ。
- 会計連携: Rp ごとに、渡す行（実施済みのオーダー・出す処方）のあとに `free` のコメントを「コメント」区分で載せる。渡す行が無い Rp のコメント、`chart` のコメントは載せない。コードは `drugCode` / `procedureCode` があればそれを、無ければ従来どおり（presetId / カタログのコード）。**Rp もコードも無い古いカルテの CSV・指紋は以前と同じ値**（テストで固定）。
- 編集画面（暫定）: コメント行は「※文」で表示・削除だけ。Rp の行で用法などを変えると同じ Rp の薬剤行にもそろえる。「左右に分ける」は左眼の行を別の Rp にする。セットを入れるときは Rp を新しい id に振り直す。

## 2. 公開マスター（基本マスター）
- 取得元: https://www.ssk.or.jp/seikyushiharai/tensuhyo/kihonmasta/ （現在は https://www.hpdx.or.jp/ へ転送。ログイン不要）。医科診療行為（s_ALL*.zip）・医薬品（y_ALL*.zip）・傷病名（b_*.zip）・修飾語（z_*.zip）。
- 作り方: `node scripts/build_eye_masters.mjs`（公開ページから最新のファイルを探して取得）。手元のファイルから作るときは `--source-dir <dir>`、廃止日の判定日は `--today YYYYMMDD`。出力は `services/eye-api/data/masters/{drug,disease,modifier,procedure}.json` と `meta.json`（取得元 URL・ファイル名・件数）。
- 2026-11-09 の取得: 医薬品 19,286 件（y_ALL20261013）・傷病名 27,684 件（b_20260601）・修飾語 2,390 件（z_20260601）・診療行為 11,837 件（s_ALL20261102）。計 10.2 MB の JSON（15 MB 未満なので圧縮・絞り込みはしていない）。
- 持つ項目: コード・名称（公表のまま）・カナ（全角にそろえる）・単位・薬価／点数。医薬品は剤形・種類の候補（`kind`: eye_drop / eye_ointment / oral / injection / other）・眼科用（`eye`: 薬価基準コード 131 か名称に点眼・眼軟膏・眼科）・薬価基準コード・一般名。傷病名は ICD-10 と眼科（H00–H59）。修飾語は接頭・接尾（区分 A8 = 接尾語）。診療行為は区分番号（例 D255）と眼科（D255–D282・J086–J091・K200–K284）。
- 利用条件: サイトの「文書・画像等の無断使用・転載の禁止」に従い、取り込んだ JSON は院内の検索（レセプト電算処理のための公開マスターの本来の用途）にだけ使い、ほかへ再配布しない。リポジトリは非公開のまま扱う。
- Cloud Run への同梱: `.gcloudignore.eye-api` に `services/eye-api/data/` を追加。
- 更新: 改定のたびにスクリプトを流して JSON を差し替える（コミット）。
- テスト用の小さな抜粋: `services/eye-api/test/fixtures/masters/`（Shift_JIS のまま数行ずつ）。

### 検索 API
`GET /v1/eye/masters/search?type=drug|disease|modifier|procedure&q=…[&limit=1..30][&eye=1]`（ログイン必須、閲覧の役割で使える）
- 全角・半角（NFKC）、ひらがな＝カタカナ、大文字小文字、空白・中黒を区別しない。名称・正式名称・一般名・カナで探す。
- 並び: 前方一致 → 部分一致。同じ中では眼科のもの → 短い名称 → コード。空白で区切った語はすべてを含むものだけ。最大 30 件。
- 応答: `{ type, q, results: [{…マスターの項目, match: "prefix"|"contains"}], available, version }`。データはプロセスの中で最初の検索のときに 1 回だけ読む。

## 3. コード
- 処方: `drugCode`（任意）。オーダー: `procedureCode`（任意）。
- 病名（カルテの `diagnoses` と患者の病名の両方）: `code`・`modifiers[]`（`{code, name, position}` の平らな配列）・`suspected`・`department`。**疑いは状態とは別のフラグ**（疑いのまま治癒・終了にできる）。古い `status: "suspected"` は「継続中（active）の疑い」として読む。どれも入力があるときだけ持たせる（古いデータの形は変えない）。会計連携の写しは従来どおり `status: "suspected"` の形で残す。

## 4. 学習リスト
`GET /v1/eye/learning-list[?category=prescription|order|diagnosis]`（カルテを書ける役割）
- この医院の確定済みカルテから、処方の Rp（薬剤＋眼・回数・用法・日数・院内外＋コメント）・オーダーの Rp（取消は除く）・病名を、使った回数の多い順に最大 50 件ずつ。
- 読む範囲: 直近 180 日・最大 500 件（`finalizedAt` の範囲と並べ替えだけなので Firestore の複合索引は不要）。修正中（下書き）は数えない。
- 医院ごとに 10 分覚えておき、確定のたびにその医院の分を捨てる。

## 5. セット
- フォルダ: `eye_set_folders`（`folderId`・`name`・`parentId`・`sortOrder`・`active`）。`GET/POST /v1/eye/set-folders`。親が無い・輪になる指定は 400。
- セットに任意の `folderId`・`sortOrder`・`diagnoses[]`・`findingsText`。一覧は `sortOrder` → 名前の順（bootstrap と `GET /v1/eye/order-sets`）。
- 作る・直す役割: `EYE_SET_ROLES`（管理者・医師）。設定画面（管理者）はそのまま使える（フォルダなど送らない項目は元の値が残る）。
- 「現在のカルテからセットを作成」: `POST /v1/eye/order-sets/from-encounter { encounterId, name, folderId?, include?, setId? }`。`include` で写す項目（処方・オーダー・病名・主訴所見・方針。既定はすべて）。新しいセットは同じフォルダの先頭（最小の sortOrder − 1）。`setId` を付けると「現在のカルテで上書き」で、写さなかった項目と並び位置は元のまま。

## 6. 確定と修正（デジカルに合わせる）
- 確定を止めるのは**記録として成り立たない行**だけ: 薬剤名の無い処方・病名の無い行・文の無いコメント行（`FINALIZE_HARD_CODES`）。それ以外（検査値の未確認・予定のままのオーダー・眼の未指定・引き継ぎ処方の未確認・眼鏡/CL の値の不整合）は `warnings`（`level: "high"`）、主訴・方針・次回の空は `level: "low"`。確定 API は `warnings` を返し、版と操作記録に `warningCodes` を残す。主訴の空は、主訴・所見の自由記載があれば出さない。
- **確定済みのカルテへの保存（PATCH）は自動で修正を始める**（医師・管理者だけ。理由は任意の `amendmentReason`、既定は「修正」）。次の確定で新しい版になる。確定した版はそのまま残る。確定前に開いていた画面からの遅れた保存（`expectedRevision` が確定後の版より古い）は 409 で止める（確定した内容を知らない保存で修正を始めないため）。変わらない保存は修正を始めない。
- `POST /amend` の理由も任意（既定「修正」）。
- 編集画面（暫定）: 確定ダイアログは止める理由が無ければ確定でき、確認事項を一覧で見せる。修正ダイアログの理由は任意。直接編集の画面は段階 2B で作る。

## 7. 主訴・所見の自由記載
- `content.findingsText`（1 欄、最大 10,000 字）。項目（section）として独立しているので、ほかの項目と同時に保存しても衝突しない。入力したカルテだけが持つ。部位別の所見（`findings`）はそのまま残る。
- 再診の前回コピーで写す。**Do・複写（入力途中のカルテへの複写）は「今回が空のときだけ入れる」**（書きかけの文には足さない。部位別の所見と同じ）。セットを入れるときも同じ。
- 差分・印刷・定型文の差し込み先（`findingsText`）に対応。編集画面では「＋ 自由記載」のチップで開く（暫定）。
