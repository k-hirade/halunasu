## 1. 製品別の調査結果

### 1.1 CLINICSカルテ（メドレー）: 最も資料が多い

**レイアウト（ヘルプから再構成）[確認済]**
- 3領域構成。
  - **左**: メニュー。「診察」（診察履歴＝過去カルテ）、投薬履歴、傷病名、サマリ、測定値など。
  - **中央**: 2号紙に相当する部分。「主訴・所見」と「処置・行為」。
  - **右**: 「オーダー」と「セット」。カテゴリを選んでフリーワードで検索し、結果をクリックすると中央の「処置・行為」に追加される。
  - 出典: https://intercom.help/clinics/ja/articles/2892066-カルテ-処置-行為を入力する
- 公式概要資料の表現は「過去診察履歴や病名等のダッシュボード、2号用紙、処置行為入力欄、検索機能などが1画面の中で完結」[ベンダー主張]。
  - 出典: https://speakerdeck.com/clinics_medley/clinicskarutegai-yao-zi-liao-ver-4-dot-01-dot-17-2-1
- **新カルテ画面（2025-11 リリース、2026-03-11 に旧画面を廃止）**[確認済]
  - 主訴・所見欄は右下のドラッグで高さを変えられ、設定はブラウザに保存される。
  - 「処置行為エリア」と「セット・オーダーエリア」の境界もドラッグで幅を変えられる。
  - 出典: https://intercom.help/clinics/ja/articles/12759289-カルテ-新カルテ画面の機能と切替について
- 主訴・所見欄はオーダーやセットの入力中は既定で隠れる。ピンアイコンで常時表示に固定できる。三点ハンドルのドラッグで幅を変え、ダブルクリックで既定幅に戻る [確認済]。
  - 出典: https://intercom.help/clinics/ja/articles/2892062-カルテ-主訴-所見を入力する
- 右上に「診察開始」、右下に「診察を完了する」がある。完了後は「本日の診察待ち一覧」ポップアップが出て、次の患者へすぐ移れる（スタッフごとに非表示にできる）[確認済]。
  - 出典: https://intercom.help/clinics/ja/articles/2892061 / https://intercom.help/clinics/ja/articles/2892077-カルテ-診察を完了する

**フォント [確認済]**
- 主訴・所見のリッチテキストは**既定の文字サイズが 14px**。ドロップダウンで変更できるが、既定値は変えられない。
- 文字色、太字、下線も使える。ツールバーアイコンはホバーで機能名が出る。
- 出典: 上記 2892062

**過去カルテの参照と Do [確認済]**
- 左メニューの「診察」で履歴を開く。
  - 日付順の一覧で、ページ送りではなく無限スクロール。
  - 日付をクリックすると個別に展開する。「開く」で全件を一括で開閉する。
- 開いた過去回の各グループ（主訴・所見、処置・行為）の右上にある「→」で、現在のカルテに転記する。
  - 処置・行為は全体でもグループ単位でも転記できる。
  - シェーマはテンプレートとマーキングごと複写でき、後から編集できる。一括転記はできない。
- 現在編集中のカルテには「編集中」バッジが付く。
- 履歴の検索: 主訴所見の本文、処置行為名、オーダーコメント、薬剤の一般名が対象。スペース区切りでAND、1語25文字以内、最大3語。全角半角と大文字小文字は区別しない。
- フィルタ: 右側にパネルが開く。条件は診療年月、保険区分、担当医、診療メニュー、オーダー種別、シェーマ・画像。同じ項目内はOR、項目間はAND。
  - **絞り込み中はフィルタアイコンが緑になる。** 選択肢はその患者に記録がある値だけを出す。
  - 同じ患者のあいだは、タブを移っても条件を保持する。
- 「過去回と今回を並べる分割表示」があるかは記載がない [未確認]。
- 出典: https://intercom.help/clinics/ja/articles/3637857-カルテ-診察履歴の確認-検索をする / https://intercom.help/clinics/ja/articles/2892082-カルテ-過去カルテの内容をコピーする-do処方をする

**セット・テンプレート [確認済]**
- 右パネルの「セット作成」で、フォルダ名、セット名、主訴、病名、処置をまとめて保存する。
- オーダーセットには検索・絞り込みがあり、フォルダラベルで分類できる。
- 処方日数の一括変更がある（https://intercom.help/clinics/ja/articles/10489450）。
- 出典: https://intercom.help/clinics/ja/articles/5486693 / https://intercom.help/clinics/ja/articles/15643040 / https://intercom.help/clinics/ja/articles/15867738

**自動保存 [確認済]**
- 診察中は自動保存される。複数のPCで同時に編集した場合は最後の入力が保存される。
- **診察完了後は自動保存が無効になり、タブごとに「保存」が必要になる。** 完了後の編集は、毎回編集履歴として残る。
- 編集履歴には「すべての保存履歴を表示」の切り替えがある（2号紙に出ない変更も表示できる）。
- 出典: https://intercom.help/clinics/ja/articles/4334418 / 2892062 / 12759289
- 保存中・保存済みのインジケータの見た目は記載がない [未確認]。

**受付一覧 [確認済]**
- ステータスは7つ: **受付待ち → 診察待ち → 診察中 → 算定待ち → 会計待ち → 完了**、および**キャンセル**。
  - ステータスは状況に応じて自動で遷移する。
  - 「診察待ち」から「受付待ち」へは戻せない。
- 絞り込み: ステータスごとのチェックボックスで表示・非表示を切り替える。医師別、診療メニュー別でも絞れる。
- 並べ替え: 診察予定、受付時刻、終了時刻の列ヘッダで昇順・降順を切り替える。
- 検索: 氏名またはカルテ番号。ひらがな入力でカタカナ名にヒットし、全角半角を問わない。電話番号は対象外。50文字まで。×でクリアする。
- 操作: 予約患者は行の右端の「受付」ボタンで受け付ける。予約なしは右上の「当日受付」。受付は「ほぼ2-3クリック」[ベンダー主張]。
- 会計エラーは赤字で表示する。
- 色分けの詳細と件数表示は記載がない [未確認]。
- 出典: https://intercom.help/clinics/ja/articles/2892057-カルテ-受付一覧画面の機能と使い方

**ショートカット**
- ヘルプに「ショートカット」の記事はない。CLINICSはマウス中心と推定される [未確認]。

**タブレット [確認済]**
- 推奨環境はWindowsまたはMacのPC。「iOS、Androidは推奨環境外」。タブレットで使うならSurfaceを推奨している。
- iPadで正式に案内しているのは、主訴所見・シェーマの手書き（Apple Pencil）と撮影画像のアップロードだけ。
- 出典: https://intercom.help/clinics/ja/articles/3595368-カルテ-ipadでのclinicsカルテの使用

**デザイン組織・技術 [確認済]**
- 2018年: カルテのUIはデザインツールを使わず、インブラウザコーディング（HTML/CSS）で作った。「医療機関ごとのカスタマイズに委ねず、開発側がUI方針を定義し一貫性ある操作性を提供する」方針。既存の電子カルテの問題として「機能ごとの複数ポップアップ」と「深い階層」を挙げている。
  - 出典: https://developer.medley.jp/entry/2018/05/18/130000/
- 2025年: 200以上の画面を持つSPA。React、Radix UI、Emotion、Storybook、reg-suit（VRT）で開発している。
  - 「電子処方箋登録ボタンだけで16の表示状態」がある。
  - 登録が成功すると、次に必要なダイアログ（服薬チェック、電子署名）を**自動で開く**。
  - 出典: https://speakerdeck.com/medley/deep-dive-into-react-component-design-for-medical-systems
- 2019年度グッドデザイン・ベスト100（CLINICS全体）。評価は「シンプルな操作性・機能と洗練されたUI/UX」。
  - 出典: https://www.medley.jp/release/clinics2019100.html

**口コミ [口コミ]**

  - 出典: https://it-trend.jp/emr_sub-withoutbeds/10109/review/193450
- 好評: 「当日の受付から会計までの流れの管理・把握がし易く」。不満は写真アップロードの枚数制限。
  - 出典: https://it-trend.jp/emr/10110/review/79886

### 1.2 エムスリーデジカル（M3）: キーボード操作の参照モデル

**カルテ画面の構成とショートカット [確認済: 公式デザイナー登壇スライド]**
- 出典: https://speakerdeck.com/yusuke109/m3design-digikar
- **左パネル（患者情報）**: 各タブに Shift+数字キーを割り当てている。

  | ショートカット | タブ |
  |---|---|
  | Shift+1 | 保険等 |
  | Shift+2 | 問診 |
  | Shift+3 | 副作用薬等 |
  | Shift+4 | バイタル |
  | Shift+5 | 検査結果 |
  | Shift+6 | 診療履歴 |
  | Shift+7 | 投薬履歴 |
  | Shift+8 | ファイル |
  | Shift+9 | サマリー |
  | Shift+0 | 傷病名 |
  | Shift+- | 定期 |

- **右パネル（セット）**: 数字キーでカテゴリを切り替える。

  | キー | カテゴリ |
  |---|---|
  | 1 | 診察 |
  | 2 | 在宅 |
  | 3 | 投薬 |
  | 4 | 注射 |
  | 5 | 処置 |
  | 6 | 手術 |
  | 7 | 麻酔 |
  | 8 | 検査 |
  | 9 | 画像 |
  | 0 | リハ他 |
  | - | 自費 |
  | ^ | 全て |

- **単キーのアクション**: B 傷病名追加、A ファイル追加、K 会計、S 保存、M 受付メモ、Shift+M 患者メモ、L 患者リスト、U 受付画面へ移動。
- **「覚える必要のないショートカット」**: ショートカットメニューはコマンドでもクリックでも使える。キーをUI上に表示し、操作しながら覚えられるようにしている。
- 方針: 「極限までシンプルかつ汎用的に」「医師の個別要望で煩雑化させない」「秒単位でこだわる」。
  - 根拠の試算: 10秒/患者 × 100人/日 × 240日 ≒ 年66時間。
- チーム構成は PdM 2、Eng 9、QA 4、Design 1。

**画面構成と技術 [確認済]**
- メインの画面は「受付画面」と「カルテ画面」の**2つに集約**し、1画面に多くの機能を載せている。AngularJSからReactへ段階的に移行し、Radix UIベースのデザインシステム「digikar-ui」を整備した。Playwright VRTとカナリアリリースを使っている。
  - 出典: https://www.m3tech.blog/entry/frontend-replacement-plan / https://www.m3tech.blog/entry/digikar-vrt
- 機能一覧 [ベンダー主張]: DO入力、シェーマ、複数スタッフでの同時カルテ表示。「処置行為自動学習」はよく使う処置行為を自動でセット化する。保存時に算定できる加算を提示する。
  - 出典: https://digikar.m3.com/feature

**モバイル戦略 [確認済]**
- PCのWebアプリが主で、iOSアプリは補完に徹している。
- **iPad手書きアプリ**: 機能は「日付ごとの予約・受付一覧」と「カルテ編集画面」に**絞り込んでいる**。シェーマは画像をキャンバスに置いて書き込む（PencilKitは画像を配置できないため不採用、自前のキャンバス）。カルテを参照する「miniPhone」をドラッグ可能なフローティングで埋め込んでいる。
- **iPhone**: 閲覧専用のビューア。フッターの8タブで各データ種別に1タップで届く。
- 出典: https://www.m3tech.blog/entry/2023/12/14/131922 / https://digikar.m3.com/news/ipad20170126

### 1.3 Henry（ヘンリー）: 中小病院向け。UX原則を公開している

- **UX原則（3つ）[確認済]**
  1. **本業に集中できる**: 必要な情報と操作が目の前にあり、迷わず実行できる。不要な情報と視線移動を避ける。
  2. **自発的に情報の有用性が改善**: 入力した情報が誰のために、何に使われるかを情報構造とUIで示す。
  3. **導入への障壁がない**: 直感的で、業務に合わせて拡張できる一貫した体験。
  - 作り手側の方針: 入力を院内コミュニケーションとして設計する、ロールごとに最適化する、**タスクではなく患者を第一の軸にする**、普遍的な基盤と制度・施設ごとのモジュールを分離する。
  - 出典: https://note.com/henry_app/n/n36c2046e4dfd
- **デザインシステム [確認済]**: Figmaで構築し、Styled Components、styled-system、Storybookで実装している。Popoverなどの複雑な操作はFloating UIに任せる。トークンの値は非公開。カルテのエディタはYjsとProseMirrorによる自前実装。
  - 出典: https://dev.henry.jp/entry/tech-stack-2023 / https://dev.henry.jp/entry/design-system-implement
- **外来会計画面 [確認済]**
  - 外来受付画面の「会計待ち」タブ → 「計算・請求」で会計画面に入る。
  - **右が当日の請求の編集、左が当日のカルテと過去の会計**という左右分割。
  - カルテ側に変更があると赤字で「変更あり」を出し、確定をブロックする。「会計に取込」で取り込む。
  - 自動算定の項目には★印が付く。右下に「確定して請求」がある。
  - 出典: https://docs.channel.io/hteensrty/ja/revisions/2aa4768d
- **受付画面の改修（2021-05）[未確認: 検索要約のみ]**: 受付画面と患者一覧で、画面遷移せずに**右側のパネルで患者情報を見られる**ようにした。
- **タブレット [ベンダー主張]**: 「iPad等のタブレットやMacにも対応」。音声入力と手書き入力がある。2026年には病棟看護・リハビリ向けのモバイルアプリを出した。
  - 出典: https://lp.henry-app.jp/ / https://prtimes.jp/main/html/rd/p/000000028.000102549.html
- **導入事例 [ベンダー主張]**
  - 「画面上のボタンの数も少なく他のカルテよりも見た目がすっきり」
  - PCに不慣れなスタッフも初日から大きなトラブルがなかった
  - 2週間〜1か月で病院全体が適応した。ベテラン看護師は「1週間ほどで慣れ」た
  - 拡大表示で読み間違いが減った
  - 出典: https://note.com/henry_app/n/ndfef4079eb68 / https://note.com/henry_app/n/n7a47e245689f

### 1.4 その他の製品

- **CLIUS（DONUTS）[口コミ]**: 「カルテ画面は、とてもシンプルで操作しやすかった」「1つの画面の中に機能が収まっていて…見やすい、感覚的に使える」。不満はORCAが別画面で、慣れが必要なこと。ベンダーは「目線の動きやクリック数を最小限」と説明している。
  - 出典: https://it-trend.jp/emr_sub-withoutbeds/8570/review/176665
- **CLIPLA Eye（眼科専用、直接の競合）[ベンダー主張・代理店記載]**
  - レフケラのデータを「見慣れたレシート形式」でカルテに表示する。
  - 検査機器の値と画像をワンクリックで取り込む。
  - **暗室用のダークモード**がある。シェーマのペンは太さ7段階・6色。
  - タブレットでの検査値入力。「1画面完結」（導入事例の見出し）。2026-10からAIサマリーで過去カルテを要約する。
  - 出典: https://www.aspicjapan.org/asu/service/15071 / https://clipla.jp/eye
- **眼科カルテ選定のUI観点（ITトレンド）**
  - 過去画像と現在画像を並べて比較できるか
  - 左右眼を分かりやすく表示できるか
  - 少ない操作で呼び出せるか
  - シェーマの色・太さ・拡大縮小
  - 出典: https://it-trend.jp/emr/article/comparison_ophthalmology

| 文字サイズの変更 | 主訴所見のリッチテキストで、選択範囲ごとに変更できる（CLINICS）。拡大表示で読み間違いが減った（Henryの事例） | 同上、note henry_app |

| 密度 | 各社とも「1画面完結」で、情報を一画面に高密度に載せる。行の高さや余白の数値は公開されていない | — |

**[推奨] Halunasu eye の目標値**: 他社の数値ではなく、上記を踏まえた提案。
- 本文（カルテ記載、所見）: 14px、行の高さ 1.5〜1.6。
- 表や一覧（受付ボード、検査値）: 13px、行の高さ 32〜36px。
- 補助テキスト: 12px が下限（CLINICSの14px既定に揃えつつ、表だけ一段締める）。
- 数値（VA、IOP、レフ）は等幅か tabular-nums で揃え、右眼と左眼を同じ列の位置に固定する。
- 色は状態の意味だけに使う（緑=適用中・正常、赤=要対応・ブロック、黄=注意）。RとLの色分けを入れる場合は、色だけに頼らず「R/L」の文字ラベルを必ず付ける。
- 暗室モードは眼科の差別化要因で、CLIPLA Eyeは既に持っている。コントラストを落としすぎず、白い面積を最小にする方向で作る。

### (3) 受付・待ちボードのベストプラクティス

1. **ステータスは業務の工程と一致させ、7つ前後に抑える**。CLINICSの実例は「受付待ち / 診察待ち / 診察中 / 算定待ち / 会計待ち / 完了 / キャンセル」。眼科なら「検査待ち / 検査中 / 散瞳待ち」などを入れる余地がある [推奨]。
2. **ステータスは操作に連動して自動で遷移させる**（カルテを開いて「診察開始」→診察中、完了→算定待ち）。手で変える操作を最小にし、逆戻りは制限する（CLINICS）。
3. **ステータスごとの表示切替**（チェックボックス、またはHenryのようなタブ「会計待ち」）。医師別、メニュー別の絞り込みも付ける（CLINICS、Henry）。
4. **列ヘッダで並べ替える**（予定時刻、受付時刻、終了時刻）。経過時間（待ち時間）の列を持つ [推奨。ドクターキューブのモニターは待ち時間と遅れ時間を表示]。
5. **行内に主要アクションを置く**（行右端の「受付」、Henryの「計算・請求」）。新規受付は右上に固定する（「当日受付」）。
6. **患者検索**: かなとカナ、全角と半角を同一視する。氏名とカルテ番号の両方で引ける。×でクリアする（CLINICS）。CLINICSは電話番号検索に対応していない（差別化の余地）。デジカルは単キー「L」で患者リスト、「U」で受付画面へ移る。
7. **一覧から離れずに詳細を見る**（右パネル、Henry）。
8. **エラーは行内に赤で出す**（会計エラー、CLINICS）。
9. **診察完了後に「次の待ち患者」を提示する**（CLINICS）。
10. **待合室と患者側**
    - モニターに待ち番号、待ち人数、待ち時間、遅れ時間を出す。音声呼び出しとテロップ（臨時休診）を使う（ドクターキューブ）。
    - **2〜4番前（約30分前）でプッシュ・メール・LINE通知**し、院外で待てるようにする。
    - 急患モードや診察停止のお知らせを1クリックで出す（FAST LIST）。
    - 呼び出しの入力は画面操作でもバーコードでもできるようにする。

### (4) 競合のレスポンシブ戦略

| 製品 | 方針 | タブレットで使える範囲 |
|---|---|---|
| CLINICS | **PCファースト**。「iOS/Androidは推奨環境外」。タブレットはSurfaceを推奨 | iPadは**手書き（主訴所見・シェーマ）と撮影アップロードだけ**を正式に案内 |
| デジカル | **PC Webが主**。iPadは推奨環境（iPadOS 18以上、Safari）だが、手書きはネイティブアプリで補完 | iPadアプリは**予約・受付一覧とカルテ編集（手書き・シェーマ・写真）に絞る**。iPhoneは閲覧専用（8タブ） |
| Henry | Web。「iPad等のタブレットやMacにも対応」 | 手書き、音声入力。病棟の看護・リハビリはモバイルアプリ |
| CLIUS | 「iPadから院内業務を一通り」[ベンダー主張] | 広め |
| CLIPLA Eye | PC中心で、タブレットは**検査値入力**に使う | 検査室での入力 |
| Medicom HRf | ノート、タブレット、スマホで閲覧。撮影画像を直接取り込む | 閲覧と撮影 |

**結論**: 主要各社はいずれも**デスクトップファースト**で、高密度の3カラムを前提にしている。タブレットは「全画面対応」ではなく、**用途を絞ったサブ画面**として提供している。用途は手書き・シェーマ、撮影、検査値入力、受付一覧、閲覧。スマホは閲覧専用か患者向けアプリ。

[推奨] Halunasu eye(Next.js)の方針:
- 1280〜1920px幅のデスクトップで3カラムを最適化する。1280px未満では右パネル（セット・オーダー）をドロワーにする。
- iPadの横向き（1024〜1366px）では、**検査値入力画面、シェーマ・手書き、受付ボード、閲覧**だけをタッチ向けに最適化する。ヒット領域は44px以上。
- スマホは閲覧専用と受付状況の確認に限る。
