## 3. チケット(すべて汎用機能。優先順は5節)

### K1: HOMIS contract拡張 v4 — multi-surfaceの「恒常事実」構造化読取

- **意図**: B/C/E/Hの共通ボトルネックは「シグナルがSOAP本文ではなく画面の構造化欄にある」こと。機器管理欄・介護/保険情報欄(要介護度・訪看頻度・MCS連携)・処方欄・カレンダー(当月訪問日)・書類を読取り、構造化事実としてリクエストに載せる。行為欄と異なりこれらは**臨床状態・体制の事実**であり入力として正当(確定原則に抵触しない)。
- **設計注意(外部レビュー2026-07-30反映)**: **書類タブは現在画面のselector追加では取得できない**。現行v3は表示中の `#pdetail_karte` のみを読み(`lib/contract.js:29`)、書類は別URL(`/homic/?pid=docs_index&patient_id=…`、`tmp/mock_homis/render.py:306`)にある。
- **具体実装**:
  - homis-mock-v4として、**現在画面surface**(介護・訪看・機器・処方・カレンダー)と**書類surface**(同一オリジンの書類ページを明示取得)を分離した**multi-surface contract**にする。surfaceごとに 患者ID一致・取得日時・取得状態(ok/unavailable)・surface hash を検証し、extractionProofと `sourceRevisionHash` に**全surfaceを含める**。書類surfaceが取得不能でも現在画面surfaceだけで計算は成立する(degraded明示、推測しない)。
  - 読取値はfee-api側の新規モジュールで typed facts へ決定論正規化(G6のfact語彙に合流: `care.certificationLevel` / `care.visitingNurseWeeklyCount` / `care.ictCoordination` / `devices[]` / `documents[]` / `encounter.monthlyVisitDays`)。**不明値はunknown、取得不能はunavailableとし、推測で埋めない**。拡張側はDOM文字列の転送のみ(dependency guard維持、innerHTML禁止)。
- **受入条件**: mock全患者で機器管理欄・訪看欄・書類surfaceの読取値がhash計測に現れる。既存v3読取に回帰なし。**denylistテスト: 行為欄 `#action_list` をどのsurfaceからも絶対に読まない**(selectorの静的検査+実行時テストの両方)。書類surface取得不能時にdegradedで計算が成立する。

### K2: 特定保険医療材料の属性リゾルバ

- **意図**: D系(交換系材料4種)の共通解。行為抽出は既に成功しており(1002実機で確認)、欠けているのは「複管/カフ付き/吸引あり/サイズ/バルーン型…」の属性から材料マスタの区分ツリーを決定論で辿る機構。
- **具体実装**: 材料マスタ(特定保険医療材料・材料価格基準=一次資料)から「材料カテゴリ→区分決定属性」の対応表をビルド時生成(G4対応表と同じ版管理・sha256・出典規約)。入力属性は (a) 本文抽出(「複管8.0mm、カフ圧確認」) (b) K1の機器管理欄(「気管切開・複管カニューレ 8.0mm」)の2源をマージ。解決結果は **exact / ambiguous / insufficient** の3値: exactのみコード確定、ambiguous(複数区分が残る)は絞った候補一覧を提示、insufficientは現行どおり「マスター検索で確認」警告(fail-closed維持)。
- **範囲の限定(外部レビュー2026-07-30反映)**: 「材料マスタ全域」を受入範囲にしない。**仕組み(対応表スキーマ・リゾルバ)は全域対応可能に作りつつ、確定対象は必要属性を公式資料で定義できたカテゴリに限定**する(第一陣: 気管切開後留置用チューブ/栄養用ディスポカテ/膀胱留置用ディスポカテ/交換用胃瘻カテの4カテゴリ)。対応表未定義カテゴリは常にinsufficient扱い。
- **受入条件**: 第一陣4カテゴリのfixtureでexact確定。属性不足fixtureでinsufficient+従来警告。ambiguous fixtureで候補が区分数まで絞られる。対応表未定義カテゴリで挙動変化なし。

### K3: 在宅療養指導管理料の包括・背反対応表(3段階の抑制強度)

- **意図**: 1002の「人工呼吸 8件から選択」偽提案の根絶と、材料算定時に手技料を出さない正しさの両方。根拠は通知の包括規定(在宅療養指導管理料を算定する場合、関連処置等は算定しない)。
- **設計注意(外部レビュー2026-07-30反映)**: 初版の「履歴・W1c候補・機器欄事実のいずれかで抑制」は**過少算定を起こす**。W1c候補や機器欄事実は「機器使用中」を示すだけで、当月の指導管理料算定を確定しない(算定しない月なら処置が正当な場合がある)。抑制強度を3段階に分ける:
  1. **生成させない**: デバイス稼働状態の記述(作動良好/常時使用/リークなし)からJ045等の処置候補を**新規生成しない**(G1述語の拡張: 状態記述と実施記述の区別は構造的規則)。これは根拠の問題であり、指導管理料の有無と無関係に常時適用
  2. **包括で抑制**: 当月の**確定明細**または要件充足済みの決定論結果として指導管理料の算定が確定している場合のみ、包括対象処置の提案を抑制し理由を1件記録(no silent caps)
  3. **確認に降格**: 親(指導管理料)が**候補段階**にすぎない場合は処置提案を削除せず、「指導管理料との包括関係を確認してください」の注記付きで残す(判断は人)
- **具体実装**: G4対応表と同じ規約で「在宅療養指導管理料ファミリ → 包括される処置コード群」を一次資料から生成し、candidate-proposal-governanceに上記3段階を実装。
- **受入条件**: (1)状態記述のみのfixtureでJ045が生成されない (2)指導管理料確定済みfixtureで処置提案が抑制+理由1件 (3)指導管理料候補段階のfixtureで処置提案が包括確認注記付きで残る (4)指導管理料非対象の患者では処置提案が無加工で残る。

### K4: 構造化候補ルール基盤の拡張(standing_family / device_management / dependent_addon)

- **意図**: G6カタログを指導管理料・従属加算へ広げる。
- **設計注意(外部レビュー2026-07-30反映)**: **現行G6へのエントリ追加だけでは実装できない**。現行の構造化事実は機器・文書の**件数のみ**(`standing-structured-triggers.js:38-87` の `deviceFactCount` 等)で種類を持たず、トリガ評価は**単一のstanding familyを選ぶ構造**(同:101-105、`familyMatches.length !== 1` で棄却)。従属加算(親ファミリに従属・施設基準要件・月次scope)を表現できない。
- **具体実装**:
  - 構造化事実を件数から**typed facts**(機器種別・文書種別・介護度・訪看頻度等)へ拡張(供給はK1)。
  - ルール種別を3分割したスキーマへ拡張: `standing_family`(現行W1c相当) / `device_management`(在宅療養指導管理料: devices種別が根拠) / `dependent_addon`(従属加算: **親ファミリ・施設基準キー・月次scope・failureMode を必須フィールドとして明示**)。すべて版管理+一次資料出典(G6スキーマ規約を継承)。
  - 第一陣エントリ: (a) 在宅酸素療法指導管理料(devices: 酸素濃縮装置等) (b) 在宅人工呼吸指導管理料(devices: 人工呼吸器) (c) 在宅気管切開患者指導管理料(devices: 気管切開カニューレ) (d) がん性疼痛緩和指導管理料(麻薬処方事実+がん性疼痛病名) (e) dependent_addon: 包括的支援(介護度+訪看頻度)/情報連携(ICT連携事実)/移行早期(診療開始日3か月以内+履歴)。
  - すべて確認候補(candidateOnly)。dependent_addonは親ファミリが確定または候補化されている場合のみ生成。月1回制約の重複チェックは履歴(J系)に委ねる。
- **受入条件**: mock該当患者のfixtureで各ファミリ・加算の確認候補が出る。親ファミリなしのfixtureでdependent_addonが出ない。devicesなし・該当病名なしで出ない(失敗方向は沈黙)。スキーマバリデータが親ファミリ・出典・scope欠落を拒否する。

### K5: 文書交付行為レーン

- **意図**: E系(指示料・情報提供料・意見書・同意書)は「文書を作成・交付した」という行為であり、本文に明示される(「特別訪問看護指示書を交付」「傷病手当金意見書を作成・交付」「療養費同意書を交付」「診療情報提供」)。R5の構造化事実分離(処方箋料等を別レーンで100%解決)と同型の**文書レーン**を作る。
- **具体実装**: 抽出契約(v15のline_role/事実)から文書事実を正規化→文書料ファミリ(B009/B012/C007/傷病手当金意見書交付料/療養費同意書交付料等)への決定論対応表(マスタ名称完全一致、G4規約)。文書事実は **created(作成)/ issued(交付)/ sent(送付)/ received(受領)** を区別し、算定候補になるのは自院のcreated/issued系のみ(receivedは過去・他院系として除外——「持参された指示書」を交付と誤認しない)。K1の書類surface(交付日=当月)が取れる場合は根拠を補強し、本文とsurfaceの不一致は確認警告。**既存LLM抽出イベントとの重複はコード+日付+根拠引用の三つ組で排除**(同一交付が本文とsurfaceの両方から二重候補化しない)。交付相手・様式の確定は人(candidateOnly)。
- **受入条件**: 1011/1012/1013相当fixtureで各文書料が候補化。交付記載のない「持参された指示書」等では出ない(past/external除外の既存述語が効くこと)。

### K6: 受診区分別の基本診療料セット(往診・電話再診・時刻加算)

- **意図**: F系。受診区分は画面から確定しているのに、往診=「再診料+往診料(+交通費)」、電話再診=「電話等再診料」の基本セットを生成していない。時刻(18:40等)も画面から取得済みで、時間帯加算は決定論判定できる。
- **設計注意(外部レビュー2026-07-30反映)**:
  - **新しい基本料マップを並立させず、既存の `outpatient_basic` 経路を拡張する**。現行は home_visit と house_call をまとめて `outpatient_basic` 削除している(`clinical-calculation-input.js:902-910`)——house_call を分離し、往診では再診料系を残して往診料を加える形に既存経路内で分岐する。
  - **時間帯判定は現行の固定祝日+8〜18時ヒューリスティック(`clinical-calculation-input.js:4786-` `receptionTimeContextWarning`、v1と自認)では不足**。**有効期間付きの施設診療時間・休日設定**をfee settingsに追加し、それを唯一の判定根拠にする(未設定なら現行どおり弱い確認警告に留める=fail-closed)。
  - 初診/再診が確定できない場合は自動確定せず**candidateOnlyの確認候補**に留める。
- **具体実装**: 受診区分(house_call/telephone_revisit)→基本診療料構成の決定論規則(点数表の基本診療料規定=一次資料)を `outpatient_basic` 推論内に実装。体制加算(時間外対応加算1・明細書発行体制等加算)は施設基準ゲート(G4)経由で自動追加。
- **受入条件**: 1012の臨時往診fixtureで再診料+往診セット、1003の18:40電話fixture(施設診療時間設定あり)で時間外加算付き電話等再診セット。施設診療時間未設定なら時間外は確認警告のみ。home_visitでは従来どおり基本料なし。既存outpatient回帰なし。

### K7: G0突合の月次スコープ判定(一対一・数量付き)

- **意図**: 月1回項目(指導管理料・在医総管等)は行為欄上「月内のどれか1訪問」に置かれる(1002は6/2、1004は月末)。訪問単位の突合では他の訪問日が全部「漏れ」に誤カウントされる。
- **設計注意(外部レビュー2026-07-30反映)**: 「同月のどこかにあれば一致」という単純規則は**不可**——1件の候補が複数の正解行を満たして一致率を水増しできる。現行実装も訪問単位のみ(`scripts/lib/fee-mock-act-coverage.mjs:85` の `matchBillableAction` は候補リスト全体に対する消費なし照合)。
- **具体実装**:
  - **患者×月×コードの数量付きmultisetとして一対一突合**する: 正解行1件は候補1件しか消費できず、候補1件も正解1件しか満たせない(数量は quantity を含めて比較)。
  - **訪問単位(per_visit)と患者×月単位(per_month)を別指標として分離**し、どちらのスコープで評価したかをレポートに明記。スコープは点数表の算定単位(月1回等)から決定論で引き、**scope判定の出典**をレポートに残す。
  - **対象月の明示実行**: 現行G0の既定は `claimMonth: "2026-06"` のみ(`scripts/evaluate_fee_mock_act_coverage.mjs:23`)。mockの正解データは5月16訪問+6月36訪問=**52訪問**あるため、5月・6月を明示指定して全訪問を基線に含める。
- **受入条件**: 1002の在宅人工呼吸指導管理料が6/23訪問の欠落に数えられない(6/2の1件と一対一で一致)。同一コードの候補1件が正解2行を満たせないことのテスト。5月・6月合計52訪問がレポート分母に現れる。per_visit項目(訪問診療料等)は従来どおり訪問単位。

### K8: 同一患家判定(cross-patient)— **別ワークオーダーに分離(データモデル先行)**

- **意図**: 1009(同一住所の2人目)は訪問診療料が再診料セットに差し替わる制度規則。患者単位で閉じる現行設計では原理的に検出不可能。
- **分離理由(外部レビュー2026-07-30反映)**: **住所のデータモデルがまだ存在しない**。platform患者契約に明示的な住所項目はなく(`platform-contracts/src/index.js:253-` の `contact` は型なしオブジェクト)、生住所を判定キーに使う設計はPHI流出リスクを伴う。本チケットは判定ロジックの前に以下の設計を要する:
  1. **訪問先モデル**: 訪問先ID、または**施設内salt付きhousehold key**(生住所の直接保存・比較を避ける)
  2. 適用期間(転居対応)・出典(どのsurface/入力から得たか)・監査イベント
  3. Firestore索引設計(org×household key×日付)
  4. **生住所をfee-apiのログ・評価結果・計測docsへ一切出さない**(hash/IDのみ)
- **判定側の設計(分離後ワークオーダーへ引き継ぎ)**: J系の患者統合を前提に、同一household key×同日訪問の組を検出し、「同一患家の可能性: 2人目以降は訪問診療料ではなく再診料になります」の**確認警告+差し替え候補**を出す。自動差し替えはしない(どちらが1人目かは訪問順=人が知る事実)。
- **受入条件(分離後)**: 1008/1009相当fixture(同一household key・同日)で警告+候補。key違い・別日では出ない。ログ・計測出力に生住所が現れない検査。J1〜J6完了+訪問先モデル実装が前提。
