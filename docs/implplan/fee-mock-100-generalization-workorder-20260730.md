# mock一致率100%と未知患者への汎用性を両立するワークオーダー(M1〜M8)

- 作成日: 2026-07-30
- status: implemented locally / STG acceptance pending
- 起点: G0初回計測 `docs/20260730-mock-act-coverage-stg/20260730_144519`(52訪問、billableMatchRate 41.5%〔6月54.1%/5月15.6%〕、missing 138件の全数分類済み)
- 目標: **mock全13患者×2か月のbillableMatchRate(確定+候補)100%**。ただし**mock専用の修正は一切行わない**——各チケットは下記3区分のいずれかに属し、患者個別・mock個別の分岐やハードコードは禁止(fee-universal-act-coverage-workorder-20260729.md 4節「汎用性ゲート」を全チケットに適用)。
- 注意: 目標指標は matched(confirmed+candidate)。管理料系はcandidateOnly設計(確定は人)のため、confirmed 100%は設計と矛盾する目標であり採用しない。

## 0. 修正の3区分(「mockだけに効くのか」への回答)

| 区分 | 意味 | 未知の患者への効き方 |
| --- | --- | --- |
| **[A] 製品汎用機能** | エンジン・レーン・契約の実装。患者の内容に依存しない構造的機構 | そのまま効く。これが本体 |
| **[B] 施設データ整備** | fee settings・施設基準・診療時間など施設単位の登録。コードではなく運用データ | 同施設の**全患者**に効く。実運用でも導入時に必ず行う作業であり、mock専用ではない(未知の患者が来ても施設設定は同じ) |
| **[C] 評価器の忠実度** | G0ハーネス・action mapの修正。製品には一切触れない | 製品挙動を変えない。「正しく測れていなかった」を直すだけ。未知患者の精度には無関係だが、**測定値の正しさ**に必須 |

**未知の患者に対する正直な整理**: 本ワークオーダー完了後、未知の患者に効くのは[A]の機構+[B]の施設設定であり、患者固有の何かには一切依存しない。ただし「mockで100%」が「未知患者で100%」を意味しない理由は2つ——(1) mockのカルテは記載が完備している(実カルテは記載漏れがあり、その場合は確認候補・警告に落ちるのが正しい挙動) (2) 抽出(LLM)の揺れ。未知患者への汎化は本書ではなく、E2コーパスdev/holdout・安定性ゲート・rolling holdout(汎用性ゲート4)で継続測定する。**mock 100%は「機構とデータが揃えば完全一致できる」ことの実証**であり、汎化性能の証明はE2系が担う。

## 2. チケット

### M1: 実行プロファイルの切替 [B]

- **訂正(2026-07-30 外部レビュー反映)**: 初版が指定した `stg-full-validation.env` は**誤り**——実物は `FEE_CLINICAL_EXTRACTION_STRATEGY_STG=whitebox_experiment`・coverage off のクロス機能回帰用プロファイルであり、00207-cdwの構成違いはまさにこれが原因。目的に合うのは **`stg-openai-primary-span-recheck.env`**(openai_primary・standingFacts=true・coverage verify・monthly enforce)。
- **内容**: STGを `stg-openai-primary-span-recheck.env` へ明示切替してデプロイ。計測レポートにreadyzのrevision+runtimeFeaturesを記録。
- **汎用性**: 製品の想定構成で動かすだけ。mock固有要素なし。
- **受入**: readyzで `clinicalExtractionStrategy: openai_primary` / `standingFactsEnabled: true` / `extractionCoverage.mode: verify` を確認してから再計測。

### M2: 計測期間の是正+施設基準登録+「版不在」の明示警告 [C]+[B]+[A]

- **訂正(2026-07-30 外部レビュー反映)**: 初版の「5月有効のfee settings追加」は**誤った処方**——設定は日付選択されずそのまま適用されており、真因はマスタ・ルールの施行日(2026-06-01)より前の診療日であること。設定を遡及させると**施行前の日付に令和8年度点数表を適用する不正**になる。また、mockの5月データ自体が令和8年度の項目名で書かれている(時代錯誤の合成データ)ため、レビュー選択肢のうち「本物の5月版マスタ導入」は**採用しない**(旧点数表とmock 5月データが整合しないため無意味)。
- **内容(計測期間の是正)[C]**: 次のどちらかで5月問題を閉じる:
  - **推奨: mock対象期間のシフト** — `prepare_homis_mock_v3.py` の対象期間を2026-07(前月2026-06)へ進め、全診療日が施行日以後になるよう再生成。G0は2026-06+2026-07の2か月で100%を測る
  - 暫定: 2026-05を100%の分母から除外し「施行前期間(文脈用途のみ)」とレポートに明記
- **内容(データ)[B]**: (a) facilityStandardsに実在届出キーを登録(`jikan_gai_taio_taisei_1`・ベースアップ(1)2系・明細書発行体制等・検体検査管理等)。**登録は根拠(届出情報)を確認できたキーのみ** (b) **`facilityStandardsConfirmed` は `false` を維持**——現settingsには「基準充足開始日は推定値」の注記付きエントリがあり(`fee-settings.json:63`)、この状態でtrueにすると未登録基準が「非該当」扱いになり候補ごと削除される(`candidate-proposal-governance.js:226-`)。全基準を根拠付きで確認するまでfalse(未確認→採用不可候補への降格が正しい挙動) (c) K6の施設診療時間・休日(有効期間付き)を登録。
- **内容(汎用機能)[A]**: **診療日に有効なマスタ・ルール版が存在しない場合の明示警告**(「当該診療日に適用可能な点数表・ルール版がありません」)。5月全滅が無警告だったのは、改定切替期の実運用でも起きる汎用の落とし穴(fail-loud化)。あわせて、fee settingsの `effectiveFrom` が現行実装で選択に使われていない事実を**有効期間付き設定選択**の将来課題として記録する(黙って施行前に適用される現状も同種の落とし穴)。
- **受入**: 是正後の全対象月で基本セット確定。施行前日付のfixtureで版不在警告1件。`facilityStandardsConfirmed=false` のまま未確認基準の候補が「採用不可候補」として残る(削除されない)こと。

### M6: K8-lite — 同日ドラフト横断+受付時刻順序による同一患家判定 [A]

- **訂正(2026-07-30 外部レビュー反映)**: 初版の「本文記載だけで差替え候補」は**不成立**——**1008(1人目)の本文にも「同一世帯として同日に訪問」が明記されている**(`patients.py:837,847`)ため、患者単体の本文では1人目/2人目を判別できず、1人目にも誤って再診料差替えが出る。
- **内容(再設計)**: 判定材料を患者単体から**同日ドラフトの横断参照**に変える:
  1. 同一org・同一施設・同一診療日のsidecarドラフト群を検索(ドラフトstoreに既に存在するデータ)
  2. **双方の本文に同一世帯・同一患家の記載がある**ドラフト組に限定
  3. **受付時刻(receptionTime——画面から取得済み)の順序**で1人目/2人目を決定
  4. **後の患者にのみ**「同一患家の2人目の可能性: 訪問診療料ではなく再診料になります」の差替え確認候補+条件コメント(「同一患家であること・訪問順を確認してください」)。**先の患者には順序確認の警告のみ**(候補は出さない)
- **自動算定の抑制境界**: `second_visit` が確定したドラフトだけ、施設恒常算定ルール由来の訪問診療料と訪問時ベースアップ評価料を算定入力から除外する。再診料セットは自動確定せず、K6 encounter-basic artifact由来の採用不可候補として提示する。`first_visit`・順序不明・相手未作成・検索不能では既存の訪問診療料を抑制しない。
- **限界の明示**: 世帯の同一性はhousehold key(K8本丸、別ワークオーダー)なしには確証できないため、これは確認候補に留まる(M7の新指標では actCoverageRecall に数え、billableReady には数えない)。本文記載のない同一患家は検出できない(沈黙=安全方向)。
- **汎用性**: org内ドラフト横断+時刻順序+本文の構造的記載のみ。患者名・mock固有要素に依存しない。
- **受入**: **1008に差替え候補が出ない**(警告のみ)。1009の2訪問で再診料セットが候補一致。片方にしか記載がないfixture・別日fixtureで発火しない。candidateOnly回帰。

### M7: 再計測と残差ゼロ化の反復(目標指標の確定定義)

- **内容**: M1→M2→M4→M3の順で適用しつつ再計測(`eval:fee-mock-act-coverage`)を回し、残missingを毎回この分類表で仕分けて、[A]ならM5/M6/M9へ、[B]/[C]なら該当チケットの漏れとして潰す。**分類できない欠落を「その他」として残さない**(全件がいずれかの区分に落ちることを完了条件にする)。
- **目標指標の確定定義(2026-07-30 ユーザー確認+外部レビューによる指標分離)**: M9で条件付き候補を広げると「一致率」が見かけ上盛れるため、指標を4つに分離する(現行評価器はcandidateを一致に含め `adoptionBlocked` も除外していない——`fee-mock-act-coverage.mjs:353-` の `candidateMatchesGold`):
  1. **actCoverageRecall = 100%**(主目標): 条件付き・採用不可候補を**含む**検知率。「行為欄の点数行がすべて確定または候補として画面に現れる」——点数を持つ行は全てbillable_lineに含まれるため「点数のある行為の検出100%」と等価
  2. **billableReadyMatchRate**(参考報告): コード確定済み・`adoptionBlocked` なし・区分選択不要の一致率。目標値は設けず実数を記録(施設基準確認等が済むほど上がる運用指標)
  3. **dangerousFalsePositiveCount = 0**(必達): 行為欄にない**確定行**。誤算定リスクであり常にゼロ
  4. **candidatePrecision**(記録+下限): 候補のうち人手仕分けで妥当と判定される率。負例fixture(出てはいけないケース)とセットで下限を設定(P2指摘反映)
  5. **コメント検知率100%**
  6. **保険点数合計の一致**: 正解行為欄のマップ済み点数合計と検出側の点数合計を訪問単位・月単位で比較。**点数合計に含めるのは確定行+コード確定済み・非ブロック・区分確定の候補のみ**(条件未確認・選択肢候補・adoptionBlockedは含めない——見かけの点数一致を作らない)。attribute行は0点、patient_chargeは保険外のため影響しないことを注記
  7. attribute/patient_chargeは一致率の分母外(前者は0点の属性行=レセプト生成側の出力、後者は保険請求外)
- **受入**: 対象全月で 1(100%)・3(0件)・5(100%)・6(点数合計一致)を達成。2・4は実数と仕分け表をレポートに記録。**同一revisionで2〜3回連続実行し、各回で上記を満たすこと**(1回きりの100%は揺れを見逃す——安定性ゲートと同思想。P2指摘反映)。

### M9: 確認候補ファースト(recall-first)への既定動作の転換 [A]・設計方針の根本修正

- **決定(2026-07-30 ユーザー決定)**: 算定要件が当日の情報だけで完全に確証できない場合の既定動作を、**「沈黙」から「条件コメント付き確認候補」に変える**。確定は人が行う(candidateOnly)ため、確認候補を広めに出すことは誤算定ではなく、漏れ(見落とし)の削減である。「とりあえず確認候補に出し、確認すべき条件をコメントで明示する」を標準とする。
- **具体実装**:
  - K4トリガスキーマの `failureMode` に **`confirm_with_note`** を追加: `requiredPositiveFacts`(発火の最低条件)と別に `humanVerifiableConditions`(人が確認すべき残条件)を持ち、最低条件が揃えば候補を出して残条件を `conditionText` に列挙する。従来の `silent` は「発火の根拠が全く無い場合」に限定
  - 既定 `silent` から `confirm_with_note` へ切り替える第一陣(いずれも**当日取得できる事実だけで発火可能**であり、J8=過去月取得を待たない):
    - **H: 薬剤総合評価調整管理料** — 本文の減薬記載(1013は「催眠薬と三環系抗うつ薬の**2剤を中止**」と当日カルテに明記)または処方欄の剤数変化を根拠に候補化。コメント「前月比2種類以上の減薬・4週以上の継続を確認してください」。前月処方(J8/K1)が取れる場合は剤数比較を根拠に昇格
    - **在宅移行早期加算** — K1のcurrentChart surfaceが**診療開始日(patientStartDate)を既に読取済み**。開始3か月以内なら候補化。コメント「初回算定年月日と算定回数上限を確認」
    - **頻回訪問加算** — K1のカレンダー(当月訪問日)から訪問回数を取得して候補化。コメント「計画外の頻回訪問に該当するか確認」
    - **在宅医療情報連携加算** — 訪看欄のICT連携表記(MCS等)から候補化。コメント「連携体制・同意の要件を確認」
  - 各エントリは従来どおり一次資料出典+版管理(K4スキーマ)。**発火根拠ゼロでの候補乱発はしない**(requiredPositiveFactsは維持——これが未知患者でのノイズ暴走を防ぐ安全条件)
  - 表示はG5の選択グループ・S2のstem/qualifier・G4の施設基準ラベルと組み合わせ、候補が増えてもUIで判断可能な形を保つ
