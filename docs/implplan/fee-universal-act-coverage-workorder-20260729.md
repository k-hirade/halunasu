# mock全患者「行為欄一致」に向けた汎用改善 ワークオーダー(G0〜G7)

- 作成日: 2026-07-29
- status: proposed(未実装)
- 目的: **未知の患者を無限に算定しても成立する汎用機能だけで**、mock全患者の行為欄(per-visit ground truth、評価専用)との突合を完全一致に近づける。患者個別・カルテ個別のチューニングは一切行わない。
- 起点となる実測: mock患者1005(2026-06-15、定期訪問、個人宅、認知症+2型DM+CKD G3b)。算定案969点 vs 行為欄9行。警告18件(重複含む)。

## 1. 患者1005で観測した失敗の型(すべてコードで発生源を特定済み)

| # | 症状 | 発生源 | 失敗の型 |
| --- | --- | --- | --- |
| 1 | 「静脈採血を施行(HbA1c・腎機能・電解質を**確認予定**)」の採血が「予定・依頼・検討の文脈」として自動算定から除外。SpO2も同様 | `packages/fee-contracts/src/clinical-predicates.js:15-18` の `isFutureOrOrderOnlyClinicalServiceContext` が**文全体**に正規表現適用。「確認予定」(結果参照の予定)の「予定」が実施済み行為を汚染。`hasBloodCollectionNegationOrPlanningContext`(:81-84)の18字距離ヒューリスティックも同根 | **文脈述語のスコープ過大**(節・係り先を見ない) |

型1が最重要。**「実施したのに確認送りになる」は取り漏れの直接原因**で、検査に限らず全行為に同じ述語が使われているため、汎用修正の効果が最も広い。型6は既存のJ系ワークオーダー(患者統合+J8過去月取得)と本書G6の併走で閉じる。

## 2. チケット

### G0: mock全患者×全カルテの行為欄突合ハーネス(効果測定の基盤)

- **意図**: 「すべてのmock患者で行為が完璧に出る」を目標にするなら、まず現在地を数値化し、G1以降の各改善の寄与を同じ物差しで測る。行為欄は評価専用という原則(算定入力に使わない)に完全に適合する使い方。
- **具体実装**:
  - mock HOMISの全患者・全カルテ日を対象に、サイドカー経路の算定案と行為欄を突合するスクリプト(`scripts/evaluate_fee_mock_act_coverage.mjs`)。
  - 行為欄の各行を4分類: `billable_line`(点数行) / `claim_comment`(830/850系コメント) / `patient_charge`(交通費等の実費) / `unknown`。J8分離ワークオーダーの分類と同一規約を共有する。
  - 指標: (a) billable一致率(算定案の確定+候補に含まれるか。確定/候補/欠落を区別) (b) comment検知率(「必要なコメント」警告で言及されているか) (c) 偽提案率(算定案にあるが行為欄にない行) (d) patient_chargeは分母から除外。
  - 出力は既存計測docs規約(本文・患者名を保存せずhashと件数)。
- **受入条件**: 全mock患者の基線レポートが `docs/2026MMDD-mock-act-coverage-baseline/` に生成される。以降のG系チケットはこのスコア差分で効果を記録する。

### G1: 文脈述語の節スコープ化と係り先判定(実施済み偽降格の根絶)

- **意図**: 型1の根絶。「予定/次回/検討」が**何に係っているか**を見ずに文全体を汚染する現行述語を、節単位+係り先語彙の判定に置き換える。特定の検査名への個別対応はしない(汎用)。
- **根拠**: 白箱側では `splitWhiteboxEvidenceClauses` で同じ問題を節分割で解決済み。同思想を主経路(OpenAI主経路のevidence検証)の共有述語に適用する。3連発した「テスト緑のまま精度だけ崩壊」と同様、述語は共有モジュール(`fee-contracts`)にあるため一箇所の修正が全経路に効く。
- **具体実装**:
  - `clinical-predicates.js` に節分割ユーティリティを追加: 句点・読点・括弧境界で分割し、**括弧内は独立節**として扱う(「施行(…確認予定)」で括弧外の「施行」と括弧内の「確認予定」を分離)。
  - `isFutureOrOrderOnlyClinicalServiceContext` 等の文脈述語は「行為語を含む最小節」に対してのみ評価するエントリポイント(`clinicalServiceContextCuesForMention(text, mention)`)を新設。既存の全文版は残すが、evidence検証(`reviewIssueFromEvidenceVerificationBlocked` に至る判定)は新エントリポイントへ移行。
  - 係り先判定: future系cue(予定/次回/後日)が「確認・結果・報告・再評価・フォロー」等の**結果参照語**に隣接する節では、行為自体のfuture文脈と見なさない。語彙表は述語モジュール内に定数として持つ(一次資料不要の言語処理規則)。
  - `hasBloodCollectionNegationOrPlanningContext` の距離ヒューリスティック(18字)は節スコープ判定に置き換えて廃止。
  - E2コーパス(train側)にパターンfixtureを追加: 「Xを施行(結果は後日確認予定)」(実施)/「Xを予定」(予定)/「Xを実施。次回もX予定」(当日分実施)/「X検討」(未実施)。**dev/holdoutには足さない**(評価の独立性維持)。
- **受入条件**:
  - 1005相当fixtureで静脈採血・SpO2が実施済み確定(evidence_verification警告が消え、採血料+検体検査が候補化)。
  - 既存のnegated-act / planned-act / past-act STGスモークケース(coverage計測8ケース)に回帰なし。
  - gold gate 2系統+安定性ゲート緑(共有述語の変更はエンジン挙動に触るため必須)。

### G2: 警告の宣言的適用条件(encounter文脈ゲーティング)

- **意図**: 型2の解消と、今後の同種ノイズの構造的抑制。個別警告のif文追加ではなく、警告生成器が適用条件を宣言できる仕組みにする。
- **具体実装**:
  - reviewIssue生成器群に共通の適用条件フィールド(例: `applicability: { encounterSettings: ["outpatient"], requiresUnresolvedVisitKind: true }`)を導入し、生成パイプラインの一箇所で評価する。
  - 第一適用: `visit_type_unknown`(`clinical-calculation-input.js:6030`)は「encounter設定が在宅系(home_visit/visit)かつ受診区分が構造化ソース(画面読取)で確定」なら生成しない。外来では現行どおり。
  - 「在宅区分の算定方針」警告(外来基本料を自動算定しない旨)が出るケースと `visit_type_unknown` が同時に出る場合は後者を冗長として抑制(同一情報の二重通知)。
- **受入条件**: 定期訪問+構造化受診区分のfixtureで初診/再診警告が出ない。外来fixtureでは従来どおり出る。既存テスト回帰なし。

### G3: 警告・確認事項の応答一元化とdedup

- **意図**: 型3の解消。UI側の対症療法ではなく、応答生成の一箇所で正規化する。
- **具体実装**:
  - `sidecarCalculationResponse`(`server.js:2145-2201`)に統合リスト `notices` を追加: warningsとreviewIssuesをreviewTopic(なければissueCode+関連イベントID+正規化メッセージ)でdedupし、severity順に並べた単一配列。
  - 既存の `warnings` / `reviewIssues` フィールドは互換のため残す(既存クライアント・テストを壊さない)。sidepanelは `notices` を表示に使う。
  - dedupキーは「同一トピックの同一対象」単位(検査コード確認×4のような同型多発は対象イベント別なら残す。ただし同一イベント同一トピックの重複は畳む)。
- **受入条件**: 1005相当fixtureで重複表示が消える(根拠確認2件・初診/再診0件〔G2後〕・検査コード確認は対象イベント数どおり)。既存レスポンス契約のスナップショットテスト維持。

### G4: 施設基準ゲートを追加提案(candidateProposals)へ適用

- **意図**: 型4の解消。検体検査管理加算で既に動いている「施設基準未登録→自動追加せず理由明示」の決定論ゲートを、管理料系proposalにも対称に適用する。未知の患者・診療科でも施設側の事実だけで判定できる汎用機構。
- **具体実装**:
  - 事前調査: 診療報酬マスタ(基本マスタ/施設基準マスタ)から「施設基準要件つき算定項目」の対応表を決定論で引けるか確認する。引ける範囲で `code → 必要施設基準キー` の対応をビルド時生成(一次資料=告示・通知の別添、出典コメント必須)。マスタから引けない項目は対象外とし、推測で対応表を書かない。
  - 提案生成の最終段で、施設基準必須項目は `facilityStandards`(fee settings)に該当キーがなければ: (a) 提案から除外し (b) 既存の施設基準確認警告と同形式で「施設基準未登録のため提案していない」を1件記録(黙って消さない=no silent caps)。
  - 認知症専門診断管理料(認知症疾患医療センター等)が第一適用例だが、実装はコード個別でなく対応表駆動。
- **受入条件**: 施設基準未登録fixtureで認知症専門診断管理料1/2が提案されず理由警告1件。施設基準を登録したfixtureでは提案される。行為欄突合の偽提案率(G0-c)が改善。

### G5: 背反グループの提案段階適用

- **意図**: 型5の解消。X系で構築済みのcanonical背反edgeをconfirmed lineだけでなく提案の表示グルーピングに使い、「同時算定不可の2件が並列提案」を「1グループから選択」に畳む。
- **具体実装**: candidateProposals生成後、canonical edge(kind 1↔2/3↔3)で結ばれたproposal同士を単一の選択グループ(`selectionGroupId` + `mutuallyExclusive: true`)にまとめ、sidecar応答の candidates に反映。解決APIの choose 系と同じ語彙を使う。
- **受入条件**: 認知症専門診断管理料1/2が1つの排他グループとして返る。背反のない提案はグループ化されない。X系の既存テスト回帰なし。

### G6: 恒常算定レーンの構造化シグナル拡張(W1c)

- **意図**: 型6の汎用解。W1(履歴)・W1b(明示文言)に加え、**「慢性疾患病名 + 在宅定期受診区分 + 処方継続」という構造化事実の組合せ**から在医総管系ファミリの確認候補を出す第3の検出源(W1c)を作る。在医総管の本質は「計画的な医学管理」であり、この3事実はその一次シグナル。1005(明示mentionなし)にも1004にも、未知の患者にも効く。
- **具体実装**:
  - `buildStandingBillingLane` に検出源を追加: `currentInputs` に既にある encounterDetails(visitKind=定期訪問)+ 当月決定論入力の処方継続事実 + 慢性疾患病名(抽出済み診断)の3条件が揃ったとき、管理料ファミリ(在医総管/施医総管系)を**確認候補**(W1b と同じcandidate形式、reviewRequired)として生成。
  - 出力は「算定対象か確認してください」の確認候補であり自動算定しない(candidateOnly)。同一建物人数・在支診区分などの区分決定は人の確認に委ね、codeCandidatesで区分候補を提示する(S2のstem/qualifier表示と整合)。
  - W1(履歴)が存在する場合はW1cを出さない(履歴駆動が優先、重複候補防止)。J系の患者統合・J8過去月取得が入れば自然にW1優先へ移行する設計。
- **受入条件**: 1005相当fixture(履歴なし・明示mentionなし)で在医総管ファミリの確認候補が出る。急性疾患のみ・外来のfixtureでは出ない。candidateOnly 3層防御の回帰テスト。

### G7: 保険外項目の突合分類(評価の正確化)

- **意図**: 型7の解消。往診交通費のような実費項目を「漏れ」と誤カウントしない。
- **具体実装**: G0の4分類に `patient_charge` の判定規則(交通費・実費・自費の語彙+マスタ非収載)を実装し、突合分母から除外。サイドカーUIへの表示追加はしない(保険請求候補のみの現行方針を維持)。
- **受入条件**: 1005の往診交通費が `patient_charge` に分類され、billable欠落に数えられない。

## 3. 優先順位と依存

1. **G0**(基線がないと効果を測れない)
2. **G1**(取り漏れの直接原因・効果範囲最大。gold gate+安定性ゲート必須)
3. **G3 → G2**(ノイズ削減。G3が表示経路を一元化してからG2の抑制を載せると検証が単純)
4. **G4 → G5**(偽提案の削減。G4の調査ステップが先行)
5. **G6**(在医総管系。J系ワークオーダーと独立に着手可、統合後はW1優先)
6. **G7**(評価の正確化。G0と同時でも可)

## 4. 非対象

- 患者・カルテ個別のプロンプト/辞書チューニング(汎用原則に反する)
- 行為欄を算定入力に使う変更(当月行為欄は評価専用。確定原則)
- 過去月行為の取得(J8分離ワークオーダー)
- サイドカーUIの操作追加(採用/却下を足さない方針)
