## 2. チケット

### G0: mock全患者×全カルテの行為欄突合ハーネス(効果測定の基盤)

- **意図**: 「すべてのmock患者で行為が完璧に出る」を目標にするなら、まず現在地を数値化し、G1以降の各改善の寄与を同じ物差しで測る。行為欄は評価専用という原則(算定入力に使わない)に完全に適合する使い方。
- **具体実装**:
  - mock HOMISの全患者・全カルテ日を対象に、サイドカー経路の算定案と行為欄を突合するスクリプト(`scripts/evaluate_fee_mock_act_coverage.mjs`)。
  - 行為欄の各行を**5分類**: `billable_line`(点数行) / `claim_comment`(830/850系コメント) / `claim_attribute`(診療年月日・単一建物診療患者数・初回算定年月日などの属性行) / `patient_charge`(往診交通費等の患家負担) / `unknown`。mock行為欄には `claim_attribute` と `patient_charge` の両方が実在する(`tmp/mock_homis/data/patients.py:363` 付近)ため4分類では足りない。**J8分離ワークオーダー(fee-sidecar-patient-auto-link-workorder-20260729.md 5.3節)の4分類もこの5分類に統一する**(同日改訂済み)。
  - 指標: (a) billable一致率(算定案の確定+候補に含まれるか。確定/候補/欠落を区別) (b) comment検知率(「必要なコメント」警告で言及されているか) (c) 偽提案率(算定案にあるが行為欄にない行) (d) patient_chargeは分母から除外。
  - 出力は既存計測docs規約(本文・患者名を保存せずhashと件数)。
- **受入条件**: 全mock患者の基線レポートが `docs/2026MMDD-mock-act-coverage-baseline/` に生成される。以降のG系チケットはこのスコア差分で効果を記録する。

### G1: 文脈述語の節スコープ化と係り先判定(実施済み偽降格の根絶)

- **意図**: 型1の根絶。「予定/次回/検討」が**何に係っているか**を見ずに文全体を汚染する現行述語を、節単位+係り先語彙の判定に置き換える。特定の検査名への個別対応はしない(汎用)。
- **根拠**: 白箱側では `splitWhiteboxEvidenceClauses` で同じ問題を節分割で解決済み。同思想を主経路(OpenAI主経路のevidence検証)の共有述語に適用する。3連発した「テスト緑のまま精度だけ崩壊」と同様、述語は共有モジュール(`fee-contracts`)にあるため一箇所の修正が全経路に効く。
- **具体実装**:
  - **既存の節スコープ処理と3本並立させない**: 主経路には既に `resolveClinicalCueScopeForEvent` / `splitClinicalClauses`(`clinical-calculation-input.js:1589-`)、白箱経路には `splitWhiteboxEvidenceClauses`(`whitebox-extraction.js:118`)が存在する。新規に3つ目を追加するのではなく、**fee-contractsに文字位置(オフセット)付きの共通スコープ解析器を1つ置き、既存2経路をそれへ移行する**。分割規則: 句点・読点・括弧境界で分割し、**括弧内は独立節**として扱う(「施行(…確認予定)」で括弧外の「施行」と括弧内の「確認予定」を分離)。移行はR2と同型のtrain/serve等価ゲート(移行前後で既存fixtureの節分割結果が変わる箇所を列挙し、変化が意図どおりであることをレビュー)を受入に含める。
  - `isFutureOrOrderOnlyClinicalServiceContext` 等の文脈述語は「行為語を含む最小節」に対してのみ評価するエントリポイント(`clinicalServiceContextCuesForMention(text, mention)`)を新設。既存の全文版は残すが、evidence検証(`reviewIssueFromEvidenceVerificationBlocked` に至る判定)は新エントリポイントへ移行。
  - 係り先判定: future系cue(予定/次回/後日)が**結果参照語**に隣接する節では、行為自体のfuture文脈と見なさない。**結果参照語彙表は1005の事例から書かない**: E2コーパスtrain split全体+mock全カルテを対象に「実施動詞と同一文内にfuture cueが共起するパターン」を機械的に列挙し、その分析から導出する(単一事例由来の語彙は過学習。R5/T1で実測した語彙ギャップと同じクラスの失敗を防ぐ)。語彙表は述語モジュール内に定数として持ち、導出元の分析をコメントで参照する。
  - **緩和の安全条件**: この修正は「確認送り→算定候補」への緩和なので、緩和が適用されるのは**行為節に実施動詞の陽性根拠(施行/実施/した/行った等)がある場合のみ**。future cueが係り先不明なだけの節は現行どおり確認送りに残す(外れたときの失敗方向を「ノイズ」側に固定し、「誤算定候補」側に倒れないようにする)。
  - `hasBloodCollectionNegationOrPlanningContext` の距離ヒューリスティック(18字)は節スコープ判定に置き換えて廃止。
  - E2コーパス(train側)にパターンfixtureを追加: 「Xを施行(結果は後日確認予定)」(実施)/「Xを予定」(予定)/「Xを実施。次回もX予定」(当日分実施)/「X検討」(未実施)。**dev/holdoutには足さない**(評価の独立性維持)。
- **受入条件**:
  - 1005相当fixtureで静脈採血・SpO2が実施済み確定(evidence_verification警告が消え、採血料+検体検査が候補化)。
  - 既存のnegated-act / planned-act / past-act STGスモークケース(coverage計測8ケース)に回帰なし。
  - gold gate 2系統+安定性ゲート緑(共有述語の変更はエンジン挙動に触るため必須)。

- **具体実装**:

### G4: 施設基準ゲートを追加提案(candidateProposals)へ適用

- **意図**: 型4の解消。検体検査管理加算で既に動いている「施設基準未登録→自動追加せず理由明示」の決定論ゲートを、管理料系proposalにも対称に適用する。未知の患者・診療科でも施設側の事実だけで判定できる汎用機構。
- **マスタの実測(外部レビュー2026-07-29、実装時に要再確認)**: 認知症専門診断管理料1・2の4コード(113022610/113022710/113014610/113042610)は現行マスタで `facility_standard_codes=[]`——**マスタからは施設基準要件を引けない**。一方、厚労省資料上は施設基準が存在する(令和8年度診療報酬改定資料 https://www.mhlw.go.jp/stf/newpage_67729.html)。※本セッションのローカルDBは空(0バイト)のため上記はレビュー実測値。実装着手時にビルド済みDBで再確認すること。
- **具体実装**:
  - **必須成果物: 一次資料(告示・通知の別添)から生成する版管理済み対応表**(`code → 必要施設基準キー`)。マスタの `facility_standard_codes` が空である以上、対応表なしにはG4は成立しない。対応表は生成スクリプト+ソース文書の版(改定年度・URL)+sha256を持ち、GCS artifactと同じ不変管理に載せる。一次資料から確認できない項目は対応表に載せない(推測禁止)。
  - **3値判定を導入**: 現行の `facilityStandards`(fee settings)は「有効な基準の一覧」であり、未登録が「未確認」か「非該当」か判別できない(`server.js:7575-` のコメント参照)。設定に完全性フラグ(例: `facilityStandardsConfirmed: boolean`)を追加し、判定を **充足 / 非充足 / 未確認** の3値にする。
  - 提案生成の最終段で: **充足**→提案する。**非充足**(完全性フラグありで未登録)→提案から除外し「施設基準非該当のため提案していない」を1件記録。**未確認**→**提案を完全削除せず「施設基準確認が必要な採用不可候補」に降格**して表示(黙って消さない=no silent caps。未確認施設で正当な算定機会を沈黙させない)。
  - 認知症専門診断管理料が第一適用例だが、実装はコード個別でなく対応表駆動。
- **受入条件**: 対応表artifactが版・出典付きで生成される。3値それぞれのfixture(充足=提案/非充足=除外+理由/未確認=採用不可候補に降格)。行為欄突合の偽提案率(G0-c)が改善。

### G5: 背反グループの提案段階適用

- **意図**: 型5の解消。「同時算定不可・同一項目の区分違いの2件が並列提案」を「1グループから選択」に畳む。
- **データの実測(外部レビュー2026-07-29、実装時に要再確認)**: 認知症専門診断管理料1と2のコード間に `electronic_exclusions` のedgeは**0件**。つまり当初の受入例(1/2を1グループに畳む)は**canonical背反edgeだけでは実現できない**。※ローカルDB空のためレビュー実測値。要再確認。
- **具体実装**(2段構え):
  - (a) **canonical edge由来のグルーピング**: edgeが実在する組に限り、proposal同士を選択グループ(`selectionGroupId` + `mutuallyExclusive: true`)に畳む。ただし**単純な連結成分をそのまま1グループにしない**: canonical edgeは `scope` / `special_condition` / 方向・解決情報を持つ(`python/medical_fee_calculation/checks_api.py:667-`)ため、scope・条件が一致するedgeのみをグルーピング根拠にし、条件付きedgeは従来どおり警告表示に留める。解決APIの choose 系と同じ語彙を使う。
  - (b) **variant-familyマスタの新設**: 認知症専門診断管理料1/2のような「同一項目の区分選択」は、一次資料(点数表の項・注の構造)から `variant family`(同一項目の区分集合)対応表を版管理付きで作り、それでグルーピングする。S2のstem/qualifier分解(名称の語幹+区分修飾)と同じ土台を共有できるかを設計時に検討する。
- **受入条件**: (a)は実在するcanonical edgeの組をfixtureにして排他グループ化を確認(認知症専門診断管理料は使わない)。(b)は認知症専門診断管理料1/2が同一variant familyとして1グループで返る。背反・同一familyでない提案はグループ化されない。X系の既存テスト回帰なし。

### G6: 恒常算定レーンの構造化シグナル拡張(W1c)

- **意図**: 型6の汎用解。W1(履歴)・W1b(明示文言)に加え、**構造化事実の組合せ**から管理料ファミリの確認候補を出す第3の検出源(W1c)を作る。
- **過学習の回避(設計原則)**: 「慢性病名+定期訪問+処方継続→在医総管」という1本のルールをハードコードしない(それは1005への個別対応にすぎない)。W1cは**standing fee familyカタログ駆動**にする: 各ファミリに「構造化事実トリガ」(受診区分・病名クラス・処方/機器/検査等の事実条件)を持たせ、トリガは各管理料の**算定要件の一次資料(告示・通知)から導出して出典コメントを付ける**。在医総管/施医総管(要件: 計画的な医学管理+定期的な訪問診療)は第一適用例であって特別扱いではない。将来ファミリを足すときはカタログにトリガを追加するだけで、レーン本体のコードは変えない。
- **カタログのスキーマ(必須フィールド)**: 各トリガエントリは (a) `version`(改定年度) (b) `source`(一次資料の出典) (c) `requiredPositiveFacts`(トリガ成立に必要な陽性の構造化事実。欠けたら発火しない) (d) `failureMode`(不成立・判定不能時の動作。常に「出さない」= 確認候補すら出さず沈黙、または「センサー警告のみ」)を持つ。**慢性病名と処方継続だけを「計画的医学管理」の証明として扱わない**——トリガはあくまで確認候補の生成条件であり、算定の根拠ではない(区分・要件充足の確定は人)。
- **具体実装**:
  - `buildStandingBillingLane` に検出源を追加: カタログ各ファミリのトリガ条件を `currentInputs`(encounterDetails・当月決定論入力の処方/機器事実・抽出済み診断)に対して評価し、成立したファミリを**確認候補**(W1bと同じcandidate形式、reviewRequired)として生成。
  - 出力は「算定対象か確認してください」の確認候補であり自動算定しない(candidateOnly)。同一建物人数・在支診区分などの区分決定は人の確認に委ね、codeCandidatesで区分候補を提示する(S2のstem/qualifier表示と整合)。
  - W1(履歴)が存在する場合はW1cを出さない(履歴駆動が優先、重複候補防止)。J系の患者統合・J8過去月取得が入れば自然にW1優先へ移行する設計。
- **受入条件**: 1005相当fixture(履歴なし・明示mentionなし)で在医総管ファミリの確認候補が出る。急性疾患のみ・外来のfixtureでは出ない。candidateOnly 3層防御の回帰テスト。

### G7: 保険外項目の突合分類(評価の正確化)

- **意図**: 型7の解消。往診交通費のような患家負担項目を「漏れ」と誤カウントしない。
- **出典確認(実装前必須)**: 「往診交通費=患家負担(保険請求点数ではない)」の根拠はC000往診料の留意事項通知「往診に要した交通費は患家の負担とする」。外部レビュー(2026-07-29)により厚労省告示PDF(https://www.mhlw.go.jp/hourei/doc/hourei/H260319S0060.pdf)で患家負担の明記が確認済みとの報告あり。実装時に当該条文を自身で確認し、判定規則のコードに出典コメント(文書名・条文・URL)を付けること。確認できない場合は `patient_charge` 分類を実装せず `unknown` に留める(推測実装禁止)。
- **repo内の傍証**: `scripts/mock_homis_build_action_map.py:61` が既に `往診交通費` をマスタ照合対象外(`is_comment_only`)としているが、理由は明文化されておらず「コメント行」と「患家負担」の区別も曖昧。G7で `patient_charge` を正式な分類として分離し、同スクリプトの分類もこれに合わせて精緻化する。
- **具体実装**: G0の4分類に `patient_charge` の判定規則(出典確認済みの項目語彙+マスタ非収載)を実装し、突合分母から除外。サイドカーUIへの表示追加はしない(保険請求候補のみの現行方針を維持)。
- **受入条件**: 一次資料の出典がコードコメントに記録されている。1005の往診交通費が `patient_charge` に分類され、billable欠落に数えられない。

## 4. 汎用性ゲート(全チケット共通の受入原則)

「特定患者で直って別患者で壊れる」を構造的に防ぐため、**本書および今後の精度改善チケットすべて**に以下を適用する。各チケットは実装時にどの機構で汎用性を担保しているかを明記すること。

1. **機構が構造的であること**: 患者の内容語(疾患名・薬剤名・検査名そのもの)をトリガにしない。判定材料は節境界・制度構造(点数表の算定要件)・マスタ・施設事実・受診区分などの構造情報に限る。内容語に依存する場合は必ずマスタまたは一次資料由来の対応表を経由する。
2. **語彙・対応表は単一事例から作らない**: 観測した失敗事例(例: 1005の「確認予定」)は失敗の**型**を特定するために使い、修正の語彙・規則はコーパス全体の分析または一次資料から導出する。観測事例のfixtureは**E2 train splitのみ**に追加し、dev/holdoutは設計に一切使わない(評価の独立性)。
3. **失敗方向が安全であること**: ヒューリスティックが未知のカルテで外れたときの挙動は「確認送り(ノイズ)」に落ちること。「誤算定候補」「無警告の除外」側に倒れる緩和は、陽性根拠(実施動詞等)の存在を条件にする。candidateOnly(確定は人)は全チケットで不変。
4. **受入は全体指標で測る**: 直した患者のケースが通ることは受入条件ではなく前提にすぎない。受入は (a) G0の全mock患者突合スコアの改善 (b) E2 dev/holdoutの回帰ゼロ (c) gold gate 2系統+安定性ゲート緑、の3点で判定する。mock患者は今後追加されるたびに**設計に使わず先に測る**(rolling holdout: 新patientの初回計測は必ず修正前後の比較で記録する)。

この4条件のどれかを満たせない修正案は、個別対応(非汎用)として本書のスコープから除外し、採用するなら明示的にその旨をdocsに記録する。
