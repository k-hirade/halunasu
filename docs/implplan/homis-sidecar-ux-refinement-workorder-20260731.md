# サイドカーUI/UX改善 ワークオーダー(UX1〜UX12)

- 作成日: 2026-07-31
- status: implemented(ローカル検証完了、STG/PRODデプロイ待ち)
- 対象: clients/homis-sidecar(sidepanel)、services/fee-api(区分絞り込み・ゾーン判定・点数2段集計)
- 前提(不変方針): 折りたたみ禁止 / 採用・却下・選択などの操作を足さない(選択はHOMIS側で人が行う) / candidateOnly / PHI(外部送出・ログはコード番号等の非PHIのみ) / DOMはcreateElementのみ・innerHTML禁止
- 背景: 実機画面(患者1004、2026-07-31)のユーザー指摘——カルテ本文の二重表示・175件のコード羅列がはみ出す・施設ルール由来の加算が「追加提案」にいる違和感・カード上のバッジとコメント全文が読まれない・「要選択+コード番号だけ」では判断不能。
- 参考調査(2026-07-31実施): Henry(会計まで画面遷移を減らす統合UI)/エムスリーデジカル(自動算定・自動チェック)/Mighty Checker等レセプトチェックソフト(警告のレベル別色分け)/しろぼんねっと(点数表・要件の定番リファレンス、令和8年対応)/ORCA(コード検索で選ぶ事務員向け設計——本サイドカーは医師向けなので「点数表の構造を日本語に翻訳する」方向で差別化)。

## 決定事項(2026-07-31 ユーザー承認)

1. カルテ本文セクションは削除(読取確認の1行に置換)
2. 生コードの列挙表示は全面禁止
3. ゾーンは出所ではなく「ユーザーの仕事」で分ける(**具体区分は外部レビュー反映後のUX3参照**。「このまま算定できる」という表示名はcandidateOnlyと矛盾するため不採用)
4. 候補カードは「算定名・点数・コード番号」の3要素のみ。施設ルールバッジ・コメント全文はカードから撤去(詳細ログへ)
5. 要選択は決定論絞り込み+残差分の日本語対比表示(本命=UX5)。**ただし区分の一意決定と算定可能性は別物として扱う**(外部レビュー反映)

## チケット

### UX1: カルテ本文セクションの削除

- **意図**: 隣にHOMIS本体が表示されており完全な二重表示。読む必要がある情報はゼロ。
- **具体実装(2026-07-31 外部レビュー反映)**: sidepanelの「カルテ本文」ブロックを削除し、ヘッダー行に「読取済み: SOAP {項目数}項目・{経過時間}前」を1行表示。
  - **注意**: 通常の読取(`halunasu:extract`)はextractionProofを持たず(proofは算定直前の `prepareCalculation()` で生成——`content.js:32-`)、`clinicalTextNodeCount` はDOMノード数であって表示上の「行数」ではない(`contract.js:77`)。したがって**初回読取レスポンスに非PHIの `extractedAt` を追加**し、表示は「SOAP {ノード数}項目・{now−extractedAt}前」とする(「行」とは呼ばない)。
- **受入条件**: 本文が表示されない。初回プレビュー時点から項目数・経過時間が出る(算定前でも表示される)。鮮度切れ時の再読取り導線が現行どおり機能。

### UX2: 生コード列挙の描画禁止+overflowガード

- **意図**: 「175件から選択」のコード羅列は情報量ゼロで、カードからはみ出す(実機で確認)。
- **具体実装**:
  - renderルール: `codeCandidates` を直接テキスト連結して描画するコードパスを削除。要約(「175区分」)+UX5の絞り込み表示のみ。
  - CSSガード: 候補カード内は `overflow-wrap` / `min-width: 0` を徹底し、いかなる文字列でもカード外へはみ出さないことをDOMテストで固定(長大文字列fixture)。
- **受入条件**: 175件fixtureでコード番号が1つも羅列されない。はみ出しDOMテスト緑。

### UX3: ゾーンの再定義(「ユーザーの仕事」基準・4区分)+安全な点数表示

- **訂正(2026-07-31 外部レビュー反映)**: 初版の `ready`(このまま算定できる)は**candidateOnlyの安全境界と矛盾**する——現行サイドカーは確定明細を含め全件 `reviewRequired: true` に変換しており(`sidecar-drafts.js:107-111` の `candidateOnlyCalculationResult`)、在宅データ提出加算も設定上 `action: "candidate"`+「要件確認のうえ採用」(`fee-settings.json` の `zaitaku_data_addon`)。コードと施設基準だけで「このまま算定」に見せるのは誤り。
- **具体実装(ゾーンは4区分)**:
  - **`included`(算定案に含まれる)**: 現在の計算結果に既に含まれる `calculated_line`。表示名は「算定案に含まれる」(「このまま算定できる」は使わない)
  - **`review_required`(要確認)**: コード・点数は確定しているが算定要件の確認が必要な提案(在宅データ提出加算はここ。**ユーザーの当初要望「追加提案から出す」は、選択ノイズと分離してincludedの直下に表示することで満たす**)
  - **`selection_required`(要選択)**: 区分選択が残る提案
  - **`blocked`(採用不可)**: 施設基準未確認・包括等
  - 判定は既存フィールド(`sourceType`/`code`/`requiresSelection`/`adoptionBlocked`)から決定論で導出し、新しい判断ロジックは持たない。記入系は現行チェックリストのまま。
- **点数表示(訂正: 全体最大値は出さない)**: 初版の「判断次第で最大+N点」の単純合算は、選択グループ・包括・親子依存・月1回制約・既存明細との重複を横断できず**正しく計算できない**(包括候補は親が候補段階だと確認付きで残る——`candidate-proposal-governance.js:91-`)。初期実装は次の3つに留める:
  1. 算定案に含まれる点数(included合計。現行の合計と同じ)
  2. 判断が必要な候補**数**(review_required+selection_required+blockedの件数)
  3. **選択グループ内だけ**の点数範囲(「875〜1,065点」等、グループ単位表示)
  - 全体最大値は排他・依存を含む最適化を実装してから別チケットで追加する。
- **受入条件**: 1004相当fixtureで在宅データ提出加算が `review_required` としてincluded直下に表示。included合計が現行合計と一致。グループ点数範囲が区分のmin/maxと一致。G0ハーネスは candidates 配列を読むため影響なし(回帰確認)。

### UX4: 候補カードの3要素化

- **意図**: カードは「算定名・点数・コード番号」だけ。読まれない装飾を撤去。
- **具体実装**:
  - カードから施設ルールバッジ・コメント全文(作成済み/要記入の従属行)を撤去。**データは削除しない**: `badges[]` / `comments[]` はレスポンスに残し、詳細ログで全文表示、要記入は現行どおりチェックリストへ、G0のコメント検知(`comments[]`参照)も不変。
  - **情報移送の契約を明示(2026-07-31 外部レビュー反映)**: 現行バッジは候補表示時にUI側で動的生成され、対応する詳細通知が常に存在するとは限らない(`sidecar-notice-view.js:127-`)。撤去にあたり**サーバがバッジ相当の情報を詳細ログ用noticeとして明示的に発行**し(candidate参照付き)、UIは推測・再構成をしない。「カードから消えた情報は必ず詳細ログのnoticeに存在する」ことをfixtureで固定。
  - コード番号は小さな副次表示(現行踏襲)。名称はstem(大)+qualifier(小)の2行(S2分解を使用)。
- **受入条件**: カードDOMが3要素+qualifier小表示のみ。撤去した全バッジ・コメントについて対応する詳細ログnoticeが存在する(網羅fixture)。UN系のfixture(2件作成済み・1件要記入)でチェックリスト・詳細ログ側の情報が欠落しない。

### UX5: 要選択の決定論絞り込み+残差分の日本語対比(本命)

- **意図**: 175件はユーザーへの丸投げ。絞り込み材料(施設基準・単一建物人数・当月訪問回数・情報通信の有無)はシステムが既に持っている。K2の3値思想(exact/ambiguous/insufficient)を管理料区分に適用する。
- **訂正2点(2026-07-31 外部レビュー反映)**:
  1. **「コードの一意決定」と「算定可能」を混同しない**。区分が1件に絞れても、月1回上限・親管理料・施設基準・包括関係は別判定。フィールドを分離する: `selectionResolution: exact|ambiguous|insufficient`(区分の絞り込み状態)と `billingEligibility: included|review_required|blocked`(UX3のゾーン)。**`selectionResolution=exact` でも原則 `billingEligibility=review_required` のまま**(includedへの昇格はしない)。
  2. **名称文字列の実行時解析で軸を判定しない**。現行にも名称regexで人数・月回数を読む処理があるが(`standing-billing-profiles.js:428-` 付近)、点数表の表記変更に脆く、表示名分解も最初の括弧で割るだけで区分軸を表現していない(`fee-candidate-display.js:24`)。**区分軸(施設類型・病床・人数・月回数・情報通信・難病等)を構造化した版管理付きartifact**をビルド時に生成し(G4規約: 出典・sha・版)、**実行時はartifactの構造化値だけで絞り込む**。名称解析はartifact生成時の検証用途に限定する。
- **具体実装(サーバ)**:
  - 上記artifactの軸値に対し決定論フィルタを適用: (a) 施設類型(施設基準キー) (b) 人数区分(単一建物人数) (c) 月回数(当月訪問回数——K1カレンダー) (d) 情報通信機器(対面訪問=非該当) (e) **難病等該当**は病名→別表(厚生労働大臣が定める疾病等)の対応が**一次資料から決定論で引ける場合のみ**適用し、引けない場合は絞らず残軸として提示(推測禁止・fail-safe)。
  - 出力: `selectionNarrowing: { selectionResolution, appliedFilters: [{axis, label, evidenceLabel}], remainingOptions: [{code, qualifierLabel, points, axisQuestion}] }`。`codeCandidates` は互換のため残す。
  - 各フィルタの `evidenceLabel` は根拠の短文(「施設基準」「単一建物6名」「当月4回訪問」)。qualifierLabelはartifactの軸値から生成する。
- **具体実装(UI)**:
  - 適用済み条件をチップ列(label ✓evidenceLabel)で表示。
  - 残差分は「軸の質問文+選択肢の対比行(qualifierLabel+点数+小さくコード)」。**表示のみで操作は無い**(選択はHOMIS側)。残り軸が2軸以上ある場合は行数が組合せで増えるため、対比行は最大6行+「他N区分(詳細ログ)」。
- **受入条件**: 1004相当fixtureで施医総管が「適用済みチップ4個+残1軸の対比(難病等該当/非該当の2行、点数付き)」になる。全軸確定するfixtureでは `selectionResolution=exact` かつ `billingEligibility=review_required` のまま「要確認(区分確定済み)」表示になる(includedへは行かない)。区分軸artifactに全エントリの出典・版・shaがある。判定根拠の各フィルタに出典(施設基準キー・画面値・カレンダー)が紐づく。絞り込み結果はG5グループ・G4施設基準ゲートと矛盾しない(既存テスト回帰なし)。

### UX6: 重要度の色体系一本化

- **意図**: 現状は緑=状態・黄=種別が混在。レセプトチェックソフト定番の「レベル別色分け」に合わせ、色は重要度だけに使う。
- **具体実装(2026-07-31 外部レビュー反映)**: 表示レベルは**サーバが `attentionLevel: required | recommended | reference` として明示的に返す**(UIでseverityから推測しない)。現行severityは4段階(critical/error/warning/info——`sidecar-notice-view.js:543-`)なので、サーバ側で4段→3段の対応を一箇所で定義(critical/error→required、warning→recommended、info→reference を既定とし、生成器が明示指定した場合はそちら優先)。UIは `attentionLevel` を色(赤系/黄系/グレー)+アイコン/文言で描画(色覚多様性対応)。
- **受入条件**: 全notice・バッジに `attentionLevel` が付く網羅性テスト(UN1のkind網羅と同型)。UI側にseverity→色の変換ロジックが存在しない(grepテスト)。

### UX7: しろぼんねっとへの参照リンク 【撤回——UX12で削除(2026-07-31 ユーザー決定)】

- **意図**: 要選択・要確認の判断材料(算定要件)への最短導線。医師が使う定番リファレンス(令和8年点数表対応)。
- **具体実装**: 候補カードのコード番号(または区分名)から `shirobon.net` の該当検索/該当ページを新規タブで開くリンクを生成。**URLに含めるのはコード番号・区分名のみ**(患者情報ゼロ)。URL形式は実装時に実サイトで確認して固定し、リンク切れ時もUI破綻しない(単なるアンカー)。
- **受入条件**: リンクhrefにコード以外のデータが含まれないテスト。dependency-guard緑。

### UX8: 再計算の差分バッジ

- **意図**: 「変化だけ見る」動線(自動算定系サービスの定番)。再計算のたびに全読みさせない。
- **具体実装(2026-07-31 外部レビュー反映)**:
  - **`sourceRevision` は使えない**——入力ハッシュが変わった時だけ増える値であり(`sidecar-drafts.js:52`)、現UIの「再計算N回目」表示(`sidepanel.js:401`)も同じ誤用。**`calculationRevision`(計算のたびに+1)を新設**し、「再計算N回目」表示もこちらへ差し替える。
  - 差分は件数差ではなく**集合差分**: draftに前回結果の安定キー集合(候補=candidateKey、警告=noticeの安定ID)を保持し、追加集合と削除集合を計算(「1件追加・1件削除」を件数差±0で見逃さない)。ヘッダーに「前回から: 候補+1/−1・点数±0」。比較はサーバ、UIは受け取るだけ。初回は非表示。
- **受入条件**: 同時に1件追加+1件削除されるfixtureで「+1/−1」が出る(±0にならない)。`sourceRevision` 不変のまま再計算した場合も `calculationRevision` が増える。初回計算では非表示。

## 追補チケット UX9〜UX12(2026-07-31 ユーザー決定)

実機確認後のユーザー決定3点+機能撤去1点。いずれも「表示の工夫より先に、出す条件を直す/出さない」方向。

### UX9: 頻回系コメント要求の常時停止

- **決定**: チェックリスト「頻回訪問の必要性コメントを記入」は**常に消す**。
- **背景**: 830100088(頻回な在宅患者訪問診療を行った必要性)・850100094(必要性を認めた診療年月日)は「頻回訪問に該当する場合」の**条件付き**コメントだが、現行エンジンは条件判定を持たず無条件に要求している。mock正解行為欄に頻回系コメントは全患者で0件であり、常時表示は過剰要求。
- **具体実装**:
  - この2コードのコメント要求生成を停止する(チェックリスト・カード・詳細ログのいずれにも出さない)。対象コードは根拠noteつきのリストで管理(「条件付きコメントであり条件判定未実装のため停止」+記載要領の出典)。
  - 850100095(訪問診療年月日=無条件・正解行為欄にも存在)は現行どおり自動生成を継続。
  - 将来、頻回該当の条件判定(記載要領の一次資料で条件確認)を実装した場合の条件付き再導入は**別判断**(本チケットでは扱わない)。
- **受入条件**: 全mockケースでチェックリストから頻回系が消える。850100095の自動生成・G0コメント検知に回帰なし(正解側に頻回系が無いため指標影響なし。将来goldに頻回系が現れた場合はG0のmissingとして検出され、再判断のトリガになる)。

### UX10: 「採用不可」の全画面撤去

- **決定**: 採用不可(blocked)は**医師・管理者どちらの画面からも消す**(前回提案の「管理者向け1行集約」も不採用)。
- **具体実装**:
  - UIはblocked候補をメイン一覧にもチェックリストにも一切描画しない。詳細ログにのみ全文(notice・audience=admin)を保持。
  - **APIレスポンスからは削除しない**: `billingEligibility=blocked` の候補・noticeはレスポンスに残す。理由: (a) G0のactCoverageRecallはblocked候補を検知として数える定義(M7)であり、消すと計測が壊れる (b) 監査・詳細ログの根拠。**表示だけを止める**。
  - ゾーン見出し「採用不可」・カードの採用不可バッジ/ラベルは全廃(二重表示問題も同時解消)。
  - 施設基準登録の導線は設定画面側の課題として非対象(登録されれば候補は自然に通常ゾーンに現れる)。
- **受入条件**: blockedを含むfixtureでメインパネルDOMにblocked由来の要素が存在しない。詳細ログには存在する。G0のrecall・blocked件数の記録が不変(ハーネスはAPIを読むため)。

### UX11: 「要選択」単独表示の廃止——常に点数(範囲)+区分ラベル

- **決定**: 「要選択」という状態名だけのカードを廃止。**ヘッダーに必ず点数を出す**。
- **具体実装**(UX5の `selectionNarrowing` / 区分軸artifactをそのまま使用):

## 追記(2026-08-03): 候補の目視確認トグル

`review_required` と `selection_required` の種別バッジを操作可能にし、
「要確認／区分確認」と「確認済み」をワンクリックで切り替える。

- 「確認済み」はSidecar上で候補内容を目視確認したことだけを表す。採用、却下、区分選択、請求確定を意味しない。
- 確認前後で `candidateOnly`、zone、区分解決状態、コード、点数、合計点、noticeを変更しない。
- UI上はトグルでも、APIは目標状態を明示する冪等な更新とし、再送による二重反転を防ぐ。
- 確認状態はSidecar draft内の専用フィールドへ、候補fingerprint・source/calculation revision・確認者・端末・日時とともに保存する。通常Feeの `reviewDecisions` は流用しない。
- 同一内容の再計算では確認を維持し、入力、マスタ、候補コード、点数、理由、区分候補が変わった場合は失効させる。
- 更新対象は最新計算の `review_required` / `selection_required` だけとし、included、blocked、採用済み・期限切れdraftはサーバ側で拒否する。
- 算定と確認更新の両方で、端末tokenの施設・診療科scopeを照合する。診療科が対象施設に属さない場合も拒否する。
- 状態変更と失効はdraft内の監査outboxへ同じtransactionで積み、event IDをdraft・候補・versionから決定する。Platform監査への冪等書き込み成功後にoutboxから削除し、失敗時は次の操作でも古いtransitionから順に補完する。
- 既存の「操作追加なし」は、算定結果を変更する採用・却下・区分選択を対象外とする方針として維持し、目視確認トグルだけを例外とする。
