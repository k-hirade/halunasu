# WX4: 自動フィードバックループ — 承認を学習資産に変える (2026-07-24)

親: [白箱抽出エンジン計画](./fee-whitebox-extraction-plan-20260724.md)。
前提: WX1〜WX3のいずれかが shadow 以上で稼働。

## 意図

candidateOnly→人承認という製品構造は、(本文, 正解構造化)のラベルを毎日生成する
**ラベル工場**である。これを自動で学習・評価資産へ還流するループを常設し、
「LLMが拾いエンコーダが取れなかったもの」「人が却下したもの」が
次のモデル世代で決定論側に移る円環を作る。改善が属人的な分析作業ではなく
仕組みで回ることが本計画の最終成果物。

## 前提整理(最初に決めるガバナンス)

1. **現時点の学習は合成データのみ**(親ページ原則3)。実カルテ・実承認データの
   学習利用は、顧客契約の利用許諾条項・匿名化規約・オプトアウト手段を整備し、
   経営判断として記録してから解禁する。本チケットの実装は
   「解禁前でも回る形」(=シグナルの収集と、合成データ生成へのフィードバック)で作る。
2. 収集するのは**構造化シグナルのみ**: 承認/却下/修正のイベント、対象コード、
   確信度、経路(encoder/LLM)、不一致種別。**本文・スパン原文は解禁まで保存しない**
   (traceの既存規約と同じ。理由コードと件数だけ)。

## 実装

### 1. シグナル収集

- **却下は正解ラベルではない(P2指摘反映)**: 却下理由には「抽出が誤り」以外に
  重複・施設基準不足・当月上限到達・臨床判断など抽出と無関係なものがある。
  却下操作に `rejectReason` の構造化選択を追加する:
  `extraction_wrong | duplicate | facility_standard_missing | frequency_limit |
  clinical_judgment | other`。学習シグナルとして使うのは `extraction_wrong`
  (負例)と承認(正例)のみで、reason未選択の却下は学習に使わない
  (集計・レポートには全て使う)。
- 収集点(全て既存イベントへのフック):
  - 明細・候補の承認/却下/修正(`decideReviewItems` 系。rejectReason付き)
  - WX1 shadowの不一致(encoder-only / LLM-only 検出)
  - WX3の合議不一致
  - 空抽出ガード発火、line_review照合リトライ
  - linker中間帯(確認事項行き)の採否
- 保存: `fee_extraction_feedback_events`(新collection。本文なし。TTL 2年)。
  保存項目(第1改訂で集計要件から逆算して確定):
  `{eventType, code, kind, category, confidence, route(encoder|llm),
    outcome(approved|rejected|corrected), rejectReason,
    specialty,           // 診療科(施設・診療科設定から決定論導出)
    encounterSetting,
    failureFeatureTags,  // 構造化タグの配列(閉集合): span_miss / wrong_code /
                         // wrong_context_axis:<軸名> / linker_low_margin /
                         // category_mismatch / body_site_expression /
                         // quantity_area_expression 等。自由文は不可
    sessionKeyHmac, orgId, occurredAt}`
  「科×カテゴリ」「処置面積表現の漏れ」等の穴レポートはこの項目から
  集計できることをレポート実装のテストで固定する(集計に必要な項目が
  欠けたイベントはスキーマ検証で保存拒否)。
  **識別子の扱い(第1改訂: 単純ハッシュは不可)**: 患者IDのような小さい値空間の
  単純ハッシュは総当たりで逆引きできる。方針:
  1. **患者識別子は保存しない**。穴レポート(カテゴリ×科の集計)に患者単位の
     追跡は不要。
  2. 重複排除・イベント相関に必要なキーは `HMAC-SHA256(org秘密鍵, feeSessionId)`
     とする。org秘密鍵はSecret Managerで管理しローテーション可能
     (ローテーション後の旧イベントは相関不能になってよい——集計用途のため)。
  3. orgIdは平文で持つ(スコープに必要。組織は秘匿対象ではない)。
  4. dependency-guard方式の機械検査に「patientId・canonicalPatientId・
     生feeSessionIdの保存禁止」を追加する。
- 集計バッチ: 週次で「エンコーダの穴 top-N(カテゴリ×科)」
  「却下率の高い候補パターン」「confidence較正のずれ」をレポート化
  (`scripts/report_extraction_feedback.mjs` → docs/へmd出力)。

### 2. 合成データ工場への還流(解禁前の主経路)

実データを学習に使えなくても、**失敗パターンの「型」は合成に還流できる**:

- 穴レポートの各項目(例:「皮膚科の処置面積表現でspan漏れ」)を
  blueprint生成のstyle-specへ追加項目として起票→E2コーパスに新セル/新ケース追加
  →次回FTの訓練・評価に自動包含。
- この「実運用の失敗型→合成ケース化」の変換だけは人が書く(週次30分想定の
  運用タスク)。それ以外は自動。

### 3. 再訓練・昇格パイプライン

- `scripts/wx_retrain.py`(WX1/WX2/WX3共通の枠):
  1. 訓練データ再生成(E2コーパス最新+マスタ最新)
  2. FT実行、モデルmanifest(データhash・ベースモデル・ハイパラ)生成
  3. **昇格ゲート自動実行**: gold 2系統 / 安定性コーパス(分散0+決定論100回一致)
     / 科×区分マトリクス(全セルで前世代比非劣化、劣化セルがあれば理由分析必須)
     / 既存反例テスト
  4. 合格したらアーティファクトをバージョン付きで登録、STG shadowへ自動デプロイ
  5. shadow計測レポート生成→**本切替だけは人が判断**(モデル昇格は
    確定行為と同格に扱う)
- 頻度: 月次を定常、マスタ改定時(6月等)は必須。
- ロールバック: アーティファクトはN世代保持、フラグでモデルバージョンをpin可能。

### 4. 実データ解禁後の拡張(設計だけ先に固定)

- 承認済みセッションから (匿名化本文, line_role, spans, codes, temporality) を
  抽出する変換器。匿名化は決定論マスキング(氏名・住所・連絡先・保険番号)+
  人のサンプル監査。
- 却下・修正はhard negative / 修正ラベルとして重み付け。
- 学習は自社管理環境のみ(外部API FTに実カルテを送らない、を既定とし、
  例外は契約で明示された場合のみ)。

## テスト・受入

- シグナル収集に本文が含まれないことのテスト(dependency-guard方式で
  禁止フィールドを機械検査)。
- 週次レポートが生成され、穴top-Nが科×カテゴリで出ること。
- 再訓練パイプラインのドライラン(小型モデル+小データ)で
  ゲート→登録→shadowデプロイまで自動で1周すること。
- 受入: **ループが実際に1周する**——穴レポート→合成ケース追加→再訓練→
  ゲート通過→shadow→(人の判断で)昇格、の全工程を1回通し、所要時間と
  改善幅(対象セルのrecall)を記録する。
