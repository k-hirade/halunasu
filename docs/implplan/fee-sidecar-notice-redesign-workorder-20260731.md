# サイドカー警告欄の解体と再配置 ワークオーダー(UN1〜UN7)

- 作成日: 2026-07-31
- status: implemented_stg_verified
- 対象: services/fee-api(notices構造化・コメント自動生成)、clients/homis-sidecar(sidepanel表示)、scripts/lib(G0コメント検知の追随)
- 背景: 実機の「警告・確認事項」が1受診で11件・全文テキストで、人間が読まない/読めない(2026-07-31 ユーザー指摘)。原因は種類の違う情報(項目の義務・出所説明・不算定説明・施設設定通知・センサー)を同一の自由文リストに流し込んでいること。
- **確定した設計判断(2026-07-31 ユーザー決定)**:
  1. 警告欄は解体し、情報を「持ち主」に付け替える(カードのバッジ/従属行・チェックリスト・提案・設定通知)
  2. **「算定しなかった理由」(継続方針の記載です等)はメイン画面から削除**。チップ化もしない。詳細ログ(監査用の別ビュー)にのみ全文を保持
  3. 決定論で値が分かるレセプトコメント(850系)はシステムが**文面を自動生成し「作成済み」状態で提示**する(警告を仕事で消す)
  4. 詳細ログは折りたたみではなく**別ビュー(別画面)**として持つ(メインパネルの折りたたみ禁止と両立)
  5. 既存方針は不変: 折りたたみ禁止・採用/却下等の操作を足さない・名前と点数が主役・candidateOnly

## 1. 現行警告の全数分類(実機11件の実例に基づく生成器→行き先の対応表)

| 生成器(現行の警告) | kind(新分類) | 行き先 |
| --- | --- | --- |
| レセプトコメントの確認(850系: 訪問診療年月日・必要性を認めた診療年月日 等、値が決定論) | `attached_comment`(status: generated) | 対象カードの従属行「コメントN件 作成済み」+文面表示(UN3) |
| レセプトコメントの確認(830系: 頻回訪問の必要性 等、自由記載) | `attached_comment`(status: input_required) | 対象カードの従属行+**チェックリスト**「◯◯のコメントを記入」 |
| 施設恒常算定ルール(〜を自動追加しました) | `line_provenance` | テキスト廃止。カードに**「施設ルール」バッジ**のみ |
| 同一患家 1人目/2人目/順序不明 判定 | `line_annotation` | 訪問診療料カードのバッジ(「同一患家・1人目」等)。2人目の差替え確認のみチェックリストにも1行 |
| 継続方針の記載です(W2意味分離の不算定説明) | `suppressed_explanation` | **メイン画面から削除**(決定事項2)。詳細ログのみ |
| 在宅区分の算定方針(外来基本料を出さない説明) | `policy_explanation` | 発火ゲート(UN5)で原則消滅。出る場合も詳細ログのみ |
| 施設基準確認(検体検査管理加算 等の未登録通知) | `facility_config` | 発火ゲート(UN5: 関連行為がある受診のみ)。出る場合はチェックリストに管理者向け1行 |
| カルテ内に未反映の可能性がある診療行為N件(カバレッジセンサー) | `sensor_candidate` | **追加提案欄へ移動**(UN4)。件数警告は廃止し、該当行の断片つき「未確認の行為」候補に |
| 施設基準未確認の採用不可候補・要選択・包括確認(G4/G5/K3系reviewIssue) | 既にproposal側にある | 提案カードのバッジ/conditionTextのまま(変更なし) |

チェックリストに残るのは `attached_comment(input_required)`・`line_annotation(2人目差替え)`・ゲート通過後の `facility_config` のみ。実例の11件は**チェックリスト2行+バッジ数個**になる。

## 2. チケット

### UN1: noticesの構造化(サーバ・G3統合リストの拡張)

- **意図**: 配置換えはUIの整形ではなく、サーバが種類を宣言することで実現する(UIに文面パースをさせない)。
- **具体実装**:
  - `sidecarCalculationNotices`(`server.js`)の各エントリに追加フィールド: `kind`(1節の enum)/`targetCode`(対象項目コード。カード従属系は必須)/`shortText`(チェックリスト・バッジ用、動詞始まり・コード番号を含めない)/`detailText`(現行全文)/`audience`(`clinician` | `admin`)。
  - **全生成器にkindを宣言させ、未分類はテストで落とす**(網羅性テスト: notices生成の全ソースがkindを持つこと。新しい警告を足すとkind宣言を強制される仕組み——今回の「箱に流し込む」再発防止の本丸)。
  - 互換: 既存 `warnings` / `reviewIssues` / `notices` 配列は維持(追加フィールドのみ)。旧クライアントは従来表示のまま。
- **受入条件**: 実機11件相当のfixtureで全noticeにkind/targetCode/shortTextが付く。kind未宣言の生成器を追加するとテストが落ちる。

### UN2: 行カード従属情報のデータ化(バッジ・コメント)

- **意図**: カードに出す情報を自由文からフィールドへ。
- **具体実装**:
  - `calculationResult.lineItems[]` / candidates に `badges[]`(`facility_rule` / `same_household_first` / `same_household_second` / `requires_selection` / `adoption_blocked` 等。既存フィールドから導出できるものは導出で)と `comments[]`(UN3の産物)を追加。
  - `施設恒常算定ルール` の警告文生成を停止し、`badges: ["facility_rule"]` に置換(出所はバッジで一目、確認文言は不要——カード自体が「承認前」表示である事実と重複するため)。
- **受入条件**: 1008相当fixtureで「自動追加しました」警告が消え、カードに施設ルールバッジが付く。

### UN3: レセプトコメントの自動生成(850系)と要記入プロンプト(830系)

- **意図**: 一番件数の多い警告を「済んでいる状態」に転換する。
- **具体実装**:
  - 必要コメント判定(現行の「レセプトコメントの確認」を出している箇所)を拡張し、**コメントコードごとに値の充足可否を決定論判定**: 850100095(訪問診療年月日)=serviceDate、850100094(必要性を認めた診療年月日)=serviceDate等、**値が算定入力から一意に決まるものは文面(和暦整形込み)を生成**して `comments[]: {commentCode, name, status: "generated", text}` に格納。
  - 値を決められないもの(830100088 頻回訪問の必要性=自由記載)は `status: "input_required"` とし、shortText「頻回訪問の必要性コメントを記入」でチェックリストへ。
  - **生成文面はあくまで提示**(サイドカーはHOMISに書き込まない・確定は人)。コピー可能なテキストとして表示。生成規則は一次資料(レセプト電算のコメントマスタの様式定義)に従い、様式が確認できないコメントコードは自動生成せずinput_required側に倒す(推測生成禁止)。
  - 和暦・日付整形は既存のレセプト出力系の整形関数を再利用し、新規実装しない(二重実装防止)。
- **受入条件**: 訪問診療料の850系2件が「作成済み」+正しい文面、830系が要記入1件になるfixture。生成規則に出典コメント。G0のコメント検知(UN7)がgeneratedを検知一致として数える。

### UN4: カバレッジセンサーの提案化

- **意図**: 「未反映の可能性N件」という行動不能な件数警告を、行動可能な候補に変える。
- **具体実装**: センサーが検出したギャップ行を、追加提案欄の `sensor_candidate` カード(「未確認の行為: 〈行の短い断片〉」+「マスター検索で確認」)として出す。断片は**画面表示のみ**(臨床者は本文を見られる立場)で、ログ・計測記録には従来どおりhashのみ(PHI規約不変)。coverage=verifyの再確認結果(K系)と重複する場合はコード+根拠で重複排除(K5の重複排除と同じ三つ組)。
- **受入条件**: 「N件あります」警告が消え、同数の候補カードが提案欄に出る。ログに断片が出ないこと。

### UN5: 発火ゲートと削除

- **意図**: そもそも出さないのが最良の圧縮。
- **具体実装**:
  1. `suppressed_explanation`(継続方針系)——**メイン画面出力を停止**(決定事項2)。詳細ログのみ。W2ゲートの動作証跡は計測・監査で引き続き参照可能
  2. `policy_explanation`(在宅区分の算定方針)——外来基本料の推論が実際に働いた受診のみ(それ以外は詳細ログのみ)
  3. `facility_config`(検体検査管理加算等)——**関連する行為が当該受診に存在する場合のみ**生成(G2の宣言的適用条件 `applicability` をこの生成器にも適用)。audience=adminを明示
- **受入条件**: 1008相当fixture(検体検査なし・外来推論なし)で両者が出ない。検体検査ありfixtureでは出る。

### UN6: sidepanelの3ゾーン化(表示)

- **意図**: 読む場所を3つに固定する。折りたたみなし・操作追加なし。
- **具体実装**:
  1. **算定案カード**(現行のまま主役): UN2のbadges/commentsを描画(バッジは短いラベル、コメントは従属行「コメント2件作成済み・1件要記入」+タップ不要の全文小活字)
  2. **確認チェックリスト**: `shortText` を持つ `attached_comment(input_required)`・`line_annotation(差替え確認)`・`facility_config` のみを列挙。**上限5行**、超過分は件数表示+詳細ビューへの導線(隠すのではなく別画面への遷移=折りたたみ禁止と両立、決定事項4)
  3. **詳細ログ(別ビュー)**: 全notice(削除分含む)のdetailTextを時系列で全件表示する別画面。監査・学習用
  - DOM生成は既存規約(createElementのみ・innerHTML禁止・dependency guard)。
- **受入条件**: 実機11件相当fixtureのレンダリングが「チェックリスト2行+バッジ」になるDOMテスト。dependency-guardテスト緑。

### UN7: G0ハーネスの追随

- **意図**: コメント検知・警告ベースの突合が文面パースに依存しているため、構造化フィールドへ移す。
- **具体実装**: コメント検知は `comments[]`(targetCode+commentCode+status)を読む。`generated` は検知一致、`input_required` も「検知」としては一致(義務の認識はできている)として数え、statusを別列で記録。同一患家コメント等、notice由来の検知も `kind`/`targetCode` 参照へ。
- **受入条件**: 既計測との互換確認(コメント検知率の定義変更をREADMEに明記)。M7指標に影響しない(kindは表示配置の宣言であり、recall/dangerous FPの定義は不変)。

### 未知noticeの扱い

全既知生成器は分類fixtureで固定する。一方、新しい未分類noticeを理由にサイドカー計算API全体を失敗させると候補も失われるため、実行時は安全側の `detail_log` に退避し、チェックリスト・候補・点数には影響させない。これは配置漏れを自動採用へつなげないfail-closedフォールバックである。
